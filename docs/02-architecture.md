# 02. システム設計

## 1. 設計の出発点

依頼の最重要要件は次の2つ。設計上のあらゆる判断はこの2点から導いている。

> **A. 顧客からLINEが来たのに、社内の誰も返信していない状態を絶対に見逃さない**
> **B. 二重通知・通知漏れ・返信済みなのに通知が続く問題を起こさない**

A と B は緊張関係にある。「見逃さない」を強めれば通知が増え、「通知しすぎない」を強めれば見逃す。
そこで **どちらに倒すかを一貫したルールとして先に決めた**。

> ### 設計原則：判定が曖昧なときは「通知する」側に倒す
>
> - 通知先の設定が解決できない → 冗長チャネルへ送り、`要確認` にする（黙って消さない）
> - 営業時間の設定が壊れている → 通知を止めず、そのまま送る
> - 送信に失敗した → バックオフして再試行し、3回失敗で `要確認` にする
> - Cron が遅延した → 期限超過分をまとめて処理する（スキップしない）
>
> 一方、**「返信済み」であることが確定している場合だけは、確実に止める**。
> これは推測ではなく `lastInboundAt <= lastOutboundAt` という検証可能な事実で判定できるため。

## 2. コンポーネント構成

単一の Next.js アプリに、以下の3つの入り口を持たせている。デプロイ対象が1つで済むため運用コストが最小になる。

| 入り口 | パス | 認証 | 役割 |
|--------|------|------|------|
| LINE Webhook | `POST /api/line/webhook` | `x-line-signature`（HMAC-SHA256） | 顧客メッセージの受信・未返信化 |
| Cron | `POST /api/cron/reminders` | `X-Cron-Secret` | 期限到来分の通知・エスカレーション・watchdog |
| 管理画面 | `/`, `/customers`, `/settings` | セッションCookie | 閲覧・返信・状態変更・設定 |

### レイヤ構造

```
app/api/*, app/*             <- 入出力（HTTP・画面）
  +-- lib/services/*         <- 副作用あり（DBトランザクション・通知送信）
        +-- lib/domain/*     <- 副作用なしの純粋関数（判定ロジック）
```

**判定ロジックを純粋関数に閉じ込めたのが設計上の要**。
営業時間・次回通知時刻・エスカレーション段階・通知本文はすべて `lib/domain/` にあり、
DBもネットワークも触らないため、境界条件を網羅的にユニットテストできる（`tests/`、77ケース）。

## 3. 未返信の状態機械

`conversations` テーブルが顧客ごとに1行あり、これが未返信状態の唯一の真実の源となる。

```
                 顧客メッセージ受信
       +-------------------------------------+
       |                                     v
  +---------+                         +--------------+
  | REPLIED |                         |   AWAITING   |<--+ 顧客の追加メッセージ
  | 返信済み |                         |   未返信      |---+ （awaitingSince を更新）
  +---------+                         +------+-------+
       ^                                     |
       |                                     | nextReminderAt 到来
       |  担当者の返信 / 手動「対応済み」        |
       |  （lastOutboundAt > lastInboundAt）  v
       |                              +--------------+
       +------------------------------| リマインド送信 |
                                      +--------------+
```

### 保持する時刻が2つある理由

| フィールド | 動き方 | 用途 |
|-----------|--------|------|
| `awaitingSince` | **顧客の追加メッセージでリセットされる** | 仕様①のリマインド起点。「最新メッセージから1時間」を実現する |
| `firstUnrepliedAt` | **返信があるまで動かない** | エスカレーション判定、ダッシュボードの経過時間、保険通知の基準 |

これを分けたのは、**仕様どおりに実装すると生じる見逃しの穴**を塞ぐため。

> 仕様①「顧客から追加メッセージが来たらカウントを最新メッセージから再スタートする」を
> そのまま実装すると、**顧客が59分おきにメッセージを送り続けた場合、リマインドが永久に発火しない。**
> 実際の不動産の問い合わせでは「すみません、あと1点」と連投されることは珍しくなく、
> しかもそういう案件ほど放置が問題になる。

そこで `firstUnrepliedAt` を別に持ち、**「返信が無い限り、無通知区間が上限（既定3時間）を超えない」** という
不変条件を保証する保険通知（`GUARD`）を入れた。設定画面の「無通知の上限」で調整でき、0 で無効化もできる。
通知本文には `未返信時間`（仕様どおりの最新基準）と `最初の未返信から`（実際の放置時間）の両方を出す。

## 4. 二重通知を防ぐ3段構え

Cron が多重起動する状況（スケジューラの重複発火、前回実行の遅延、複数インスタンス）は現実に起きる。
これを **3層で防いでいる**。

### 第1層：行の原子的な確保（claim）

期限到来した会話を、1つの SQL 文で「取得と同時に予約時刻を先送り」する。

```sql
WITH due AS (
  SELECT id FROM conversations
  WHERE "replyState" = 'AWAITING'
    AND "nextReminderAt" IS NOT NULL
    AND "nextReminderAt" <= $now
  ORDER BY "nextReminderAt" ASC
  LIMIT $batch
  FOR UPDATE SKIP LOCKED      -- 他ワーカーが掴んだ行は飛ばす
)
UPDATE conversations c
SET "nextReminderAt" = $leaseUntil    -- 5分先へ = 確保
FROM due WHERE c.id = due.id
RETURNING c.id
```

`SKIP LOCKED` により、同時に走る複数のワーカーは**互いに素な集合**を取得する。

**確保は「削除」ではなく「5分間のリース」である点が重要。**
送信処理の途中でプロセスが落ちても、5分後には別の実行が同じ行を拾い直す。
= プロセス障害による通知漏れが構造的に起きない。

### 第2層：冪等キーの UNIQUE 制約

送信前に `reminders` へ行を作る。`dedupeKey` に UNIQUE 制約があるため、
万一2つのワーカーが同じ会話を掴んでも、INSERT は1つしか成功しない。

```
ROUTINE     : r:{conversationId}:{firstUnrepliedAt}:{回数}
GUARD       : g:{conversationId}:{firstUnrepliedAt}:{回数}
ESCALATION  : e:{conversationId}:{firstUnrepliedAt}:{ruleId}   <- 1サイクル1ルール1回
WATCHDOG    : w:{conversationId}:{firstUnrepliedAt}:{時間バケット}
```

サイクル識別子に `firstUnrepliedAt`（返信が来るまで動かない時刻）を使っているため、
**担当者が返信して新しい未返信サイクルが始まれば別のキーになり、次の通知が誤って抑止されることはない。**

### 第3層：送信直前の再判定

確保した行を再読込し、送信の直前にもう一度 `lastInboundAt > lastOutboundAt` を検証する。
偽なら送らずに `nextReminderAt` を NULL にする。
「返信した1秒後にリマインドが飛ぶ」ケースをここで潰している。

同時に、返信を記録する側（`recordOutboundMessage`）も **同一トランザクション内で** `nextReminderAt` を NULL にする。
両方向から閉じているため、どちらの順序で処理が走っても矛盾しない。

## 5. 通知漏れを防ぐ仕組み

| 障害 | 対策 |
|------|------|
| Cron の実行が数回失敗した | 「1時間ごとに起動して送る」ではなく「**期限を過ぎたものを全件処理する**」設計。遅延しても必ず回収される |
| 送信中にプロセスが落ちた | 確保は5分リース。期限切れで自動的に再取得される |
| LINE API がエラーを返した | `2 → 5 → 15 → 30分` の指数バックオフで再試行。全宛先が失敗したら冗長Webhookへフォールバックし、3回失敗で `要確認` |
| 通知先が1つも設定されていない | 送信を諦めず、冗長チャネルへ送って `要確認` に落とす。設定画面にも警告を出す |
| Cron自体が停止した | ① `/api/health` が最終実行からの経過を返し、外部監視でアラート<br/>② ダッシュボード上部に赤帯で警告<br/>③ 復旧後、watchdog が滞留分を `要確認` にして管理者へ通知 |
| 一部の宛先だけ届かなかった | 宛先ごとに成否を記録。**1件でも成功すれば配信成功**とし、失敗分は `reminders.error` に残す |

## 6. 複数担当者の同時操作

- `conversations.version` による**楽観ロック**。管理画面は取得時の version を送り、
  サーバー側で不一致なら `409` を返して「他の担当者が更新しました」と表示する。
- 通知先は**必ず宛先キー（チャネル種別+宛先）で重複排除**するため、
  1人が担当者かつ責任者かつ管理者であっても届く通知は1通。
- 返信は誰が行っても同じ `conversations` 行を更新するため、「Aさんが返信したのにBさん宛の通知が続く」ことはない。

## 7. 営業時間の扱い

- 営業時間外の通知は **スキップではなく繰り延べ**。次の営業開始時刻へ `nextReminderAt` を動かす。
  スキップにすると、金曜20:00に来た問い合わせが月曜まで一度も通知されない可能性がある。
- 曜日ごとに営業/休業と時間帯を設定でき、土日も個別に指定できる。
- 祝日・臨時休業日はテーブルで管理。`isOpen=true` で「臨時営業日」も表現できる。
- `countBusinessHoursOnly` を有効にすると、経過時間そのものを営業時間だけで数える
  （夜間・休日の滞留時間を「未返信2時間」に含めたくない場合に使う）。
- **全曜日が休業に設定されているなど判定不能な場合は、通知を止めずそのまま送る**（フェイルセーフ）。

## 8. エスカレーション

`escalation_rules` は「経過時間の閾値」と「誰を追加するか」の対応表。

```
 1時間 -> 担当者
 3時間 -> 担当者 + 責任者
 6時間 -> 担当者 + 責任者 + 管理者 + 共通グループ
```

- 到達済みのルールの宛先を**すべて合算**して重複排除するため、6時間時点では全員に1通ずつ届く。
- 閾値を新しく跨いだ瞬間は、**通常の間隔を待たずに**エスカレーション通知を出す。
  （通知間隔を3時間に設定していても、1時間のエスカレーション設定があれば1時間で通知される）
- 各ルールは1サイクルにつき1回だけ発火する（`dedupeKey` による）。
