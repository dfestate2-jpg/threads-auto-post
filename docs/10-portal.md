# 業務システムポータル（DFエステートシステム）

社内で使う業務システムの入口を1か所にまとめる画面。
ログインすると、登録されているシステムがアプリのアイコンのように並び、
押すとそのシステムへ移動する。

- トップページ … `/portal`
- システム管理 … `/portal/admin`（管理者のみ）

---

## 1. なぜこの構成にしたか

### 既存の管理画面と同じアプリに載せる

ポータルを別サイトとして立てると、ログイン・ユーザー・権限を二重に持つことになる。
同じアプリに載せれば、既存の `users` テーブルとセッションCookieをそのまま使えるので、
**利用者は1回ログインするだけ**で済み、担当者の追加も1か所で終わる。

将来ここへ「利用状況」「お知らせ」「通知」を足すときも、
すでに顧客・担当者・設定が同じDBにあるため、繋ぎ込みの作業が要らない。

### URLをコードに書かない

これがこの機能の中心にある要件。
システムの引っ越しやドメイン変更のたびにコードを直してデプロイするのは現実的ではないので、
遷移先URLは `portal_systems` テーブルに持ち、画面はサーバー側でその値から描く。

管理画面でURLを変えれば、**次に開いた時点で新しい遷移先に切り替わる**。
デプロイもキャッシュ削除も要らない（ページは `dynamic = 'force-dynamic'`）。

### システムが増えてもコードを触らない

カードは `portal_systems` の行をそのまま並べているだけなので、
新しいシステムが増えても行を1件足すだけで済む。
「LINE管理」「物件管理」「売上管理」…と増えていっても、修正するファイルは無い。

## 2. データベース

`portal_systems` テーブル 1 つ。

| 列 | 意味 |
| --- | --- |
| `name` | システム名（カードの見出し） |
| `icon` | アイコン。絵文字をそのまま保存する |
| `accent` | カードの色。`slate` `blue` `emerald` などのキー |
| `description` | 説明文。カードの2行目 |
| `url` | 遷移先。`https://` の絶対URL、または同一サイト内の `/path` |
| `openInNewTab` | 別タブで開くか。外部システムは既定でオン |
| `sortOrder` | 表示順。小さいほど先 |
| `published` | 非公開にするとトップページから消える（削除ではない） |
| `minRole` | このシステムを開ける最低権限 |

アイコンライブラリを入れず絵文字にしたのは、
**管理画面から自由に変えられること**を優先したため。
アイコン集から選ぶ方式にすると、候補に無いものを使いたくなった時点でコード修正に戻ってしまう。

### 色を「キー」で持つ理由

Tailwind は文字列を連結して作ったクラス名を抽出できない。
DBに `bg-blue-100` のようなクラス名を直接入れるとビルド時に削られて色が出ないため、
DBにはキーだけを入れ、クラス名は `src/lib/domain/portal.ts` の `ACCENTS` 対応表で解決している。

### 表示順を 0, 10, 20 … で振る理由

並び替えのたびに全件へ連番を振り直す方式にしている。
「1つ上へ」を押したら配列を入れ替えて、0 から 10 刻みで振り直す。
歯抜けや重複が起きないので、あとから見て順序が分からなくなることがない。

## 3. 画面

### トップページ `/portal`

ヘッダー（サービス名・設定・ユーザー・ログアウト）と、システムカードのグリッド。
スマホは2列、タブレットは3列、PCは4列に折り返す。

1件も登録されていないときは白紙にせず、
管理者には「設定画面を開く」、それ以外の人には「管理者が登録すると表示されます」と出す。

### システム管理 `/portal/admin`

追加・編集・削除・URL変更・アイコン変更・表示順・公開/非公開をここで行う。

管理者以外が開いた場合はログイン画面へ飛ばさず、
「この画面は管理者だけが開けます」と理由を見せて一覧へ戻れるようにしている
（ログイン済みの人をログイン画面へ送ると、何が起きたのか分からないため）。

---

## 4. 権限

`minRole` で「そのシステムを一覧に出す最低権限」を指定できる。

| 設定 | 見える人 |
| --- | --- |
| 全員（`STAFF`） | 全員 |
| 責任者以上（`MANAGER`） | 責任者・管理者 |
| 管理者のみ（`ADMIN`） | 管理者 |

絞り込みは `listVisibleSystems()` の中だけで行う。
画面側で条件を書くと、ページが増えたときに書き漏らして
「本来見えないはずのカードが出る」事故が起きるため。

将来「このシステムはこの担当者だけ」といった細かい権限が必要になったら、
`portal_systems` と `staff` の中間テーブルを足す。既存の行は `minRole` のまま動く。

---

## 5. URLの検証

管理画面から登録できるURLは次の2種類だけ。

- `http(s)` の絶対URL
- 同一サイト内のパス（`/` で始まる。`//host` は外部サイトなので除外）

`javascript:` や `data:` を登録できてしまうと、
カードを押した利用者のブラウザで任意のスクリプトが動く入口になる。
検証は `normalizeSystemUrl()` に集約し、画面とAPIの両方が必ずここを通る
（管理画面では弾かれるがAPIからは通る、という穴を作らないため）。

スキームを書かずに `example.com/remind` と入力された場合は `https://` を補う。
URLに詳しくない人が登録することを想定しているため。

## 6. 初期データ

`ensureBaselineData()`（初回セットアップ / `npm run seed`）で、
実在するシステムだけを1件登録する。

- 🔔 リマインドシステム → `/`

まだ存在しないシステムをダミーURLで作っておくと、
押した人が「壊れている」と受け取ってしまうため入れない。
顧客管理や営業ダッシュボードは、URLが決まった時点で管理画面から追加する。

ポータルを後から足した環境には初期データが入らないので、
管理画面に「初期カードを入れる」ボタンを置いてある（1件でもあれば何もしない）。

---

## 7. 追加のしかた（運用）

1. 管理者でログインし、`/portal/admin` を開く
2. 「＋ システムを追加」を押す
3. システム名・URL・説明・アイコン・色・表示できる人を入力して保存
4. トップページに戻ると、カードが増えている

一時的に隠したいだけなら「非公開にする」を使う。削除すると元に戻せない。

---

## 8. これから足せるもの

この画面は単なるリンク集ではなく、業務システムの入口として育てる前提で作ってある。

- **利用状況** … カードのリンクを `/portal/go/[id]` の中継に変え、通過を記録する
- **お知らせ・通知** … トップページのグリッド上部に領域を足す
- **テナント管理** … `portal_systems` に `tenantId` を足し、一覧の絞り込み条件に加える
- **システム別のアクセス権限** … `minRole` を中間テーブルに置き換える

いずれも `listVisibleSystems()` と `portal_systems` の周りだけで完結し、
カードの描画やトップページには手を入れずに済む。
