# 01. 実装前整理（API / アカウント / DB / 構成 / コスト / セキュリティ）

本ドキュメントは、依頼された「公式LINE 未返信リマインドシステム」を実装するにあたり、
着手前に確定させておくべき前提条件を整理したものである。

---

## 1. 必要なAPI

| # | API | 用途 | 必須 | 備考 |
|---|-----|------|------|------|
| 1 | **LINE Messaging API — Webhook** | 顧客からの受信メッセージを取得 | ✅ 必須 | `POST /api/line/webhook`。`x-line-signature` の HMAC-SHA256 検証が必須 |
| 2 | **LINE Messaging API — Push Message** (`POST /v2/bot/message/push`) | 社内LINEへのリマインド通知 / 管理画面からの顧客返信 | ✅ 必須 | 課金対象メッセージ |
| 3 | **LINE Messaging API — Reply Message** (`POST /v2/bot/message/reply`) | 顧客への即時返信（replyToken 使用） | 推奨 | **無料**（無料メッセージ通数にカウントされない）。replyToken は約1分・1回のみ有効 |
| 4 | **LINE Messaging API — Get Profile** (`GET /v2/bot/profile/{userId}`) | 顧客の表示名・アイコン取得 | ✅ 必須 | 顧客名の初期値として使用 |
| 5 | **LINE Messaging API — Get Group Summary / Member IDs** | 社内グループへの通知先確認 | 任意 | 認証済みアカウントのみ利用可 |
| 6 | **Webhook (汎用 / Slack Incoming Webhook 互換)** | 社内通知の代替・冗長経路 | 推奨 | LINE通数削減とフェイルオーバー用（後述） |
| 7 | **内部 Cron API** (`POST /api/cron/reminders`) | 定期実行でリマインド判定・送信 | ✅ 必須 | `X-Cron-Secret` による認証 |

### ⚠️ 最重要の技術的制約：LINE公式アカウントの「担当者返信」は Webhook に流れてこない

LINE Messaging API の Webhook は **顧客→公式アカウント方向のイベントのみ**を配信する。
**LINE Official Account Manager（チャット画面）から担当者が手動で送った返信は、Webhook イベントとして通知されない。**
（配信されるイベント： `message` / `unsend` / `follow` / `unfollow` / `join` / `leave` / `memberJoined` / `memberLeft` / `postback` / `videoPlayComplete` / `beacon` / `accountLink` / `things` / `membership`）

つまり **「担当者がLINE公式アカウントManagerから返信した」ことをシステムが自動検知する公式手段は存在しない。**

本システムでは以下 4 経路で返信を捕捉し、「対応済み」判定の取りこぼしを防ぐ。
詳細は [`docs/07-line-reply-detection.md`](./07-line-reply-detection.md) を参照。

| 経路 | 検知確実性 | 運用 |
|------|-----------|------|
| **A. 管理画面から返信**（Messaging API push/reply を本システムが実行） | ◎ 100% | **推奨。返信窓口を管理画面に一本化すれば完全自動判定になる** |
| **B. 管理画面で「対応済み」ボタン** | ○ 手動 | LINE Managerで返信した場合の補完 |
| **C. 返信取り込みAPI** `POST /api/ingest/outbound` | ○ | 外部連携（LINE Module Channel / iPaaS / CRM）からの返信通知を受ける口 |
| **D. 未対応ガード（保険）** | ◎ | B/C が実行されなくても通知が止まらないため、必ず誰かが気付く＝「見逃さない」要件は満たされる |

> 設計方針：**「返信済みなのに通知が続く」より「未返信なのに通知が止まる」方が事故として重大**であるため、
> 曖昧な状態では通知を止めない（フェイルセーフ = 通知継続）。

## 3. 必要なデータベース

**PostgreSQL 14+**（Supabase / Neon / RDS / 自前いずれでも可）を採用する。

### 選定理由
- **トランザクション + 行ロック（`SELECT ... FOR UPDATE SKIP LOCKED`）が必須。** 本件の中核要件である「二重通知の防止」は、複数のCronワーカーが同時に走っても1件のリマインドが1回しか送られないことを保証する必要があり、これは RDB の行ロックが最も確実。
- **一意制約（UNIQUE）による冪等性担保。** LINE Webhook の再送、Cronの重複起動、いずれも UNIQUE 制約で吸収する。
- 無料枠が実用的（Supabase 500MB / Neon 0.5GB）。本システムのデータ量は 1万件/年程度で数十MB。

### 主要テーブル（詳細は [`docs/03-database-design.md`](./03-database-design.md)）

| テーブル | 役割 |
|---------|------|
| `customers` | 顧客（LINEユーザー）マスタ・担当者割当・通知間隔の個別設定 |
| `conversations` | **中核。** 未返信状態機械（最終受信/最終返信/経過起点/次回通知時刻/リマインド回数/対応状況） |
| `messages` | 送受信メッセージ全ログ |
| `reminders` | 送信したリマインドの記録。**冪等キーによる二重送信防止** |
| `staff` | 社内担当者（LINEユーザーID・役割・通知先） |
| `escalation_rules` | 経過時間に応じたエスカレーション設定 |
| `app_settings` | 営業時間・既定通知間隔・タイムゾーン等のシングルトン設定 |
| `business_holidays` | 祝日・臨時休業日 |
| `webhook_events` | LINE Webhook の冪等性担保（`webhookEventId` UNIQUE） |
| `users` | 管理画面ログインユーザー |
| `audit_logs` | 操作監査ログ |

```
   │                       ▼                            │          │
   │            ┌──────────────────────┐                 │          │
   │            │ ドメイン層(純粋関数)   │◀────────────────┘          │
   │            │ 営業時間 / 次回通知    │                            │

              ┌────────────┴─────────────┐
              ▼                          ▼
   ┌─────────────────────┐    ┌────────────────────────┐
   │ PostgreSQL          │    │ 通知ディスパッチャ        │
   │ (Supabase / Neon)   │    │  ├ LINE push (チャネル②) │──▶ 社内LINEグループ
   │  行ロックで排他制御   │    │  ├ LINE push (個人)      │──▶ 担当者個人LINE
   └─────────────────────┘    │  └ 汎用Webhook (冗長)    │──▶ Slack等
                              └────────────────────────┘
                           ▲
                           │ 毎分 or 5分ごと
                  ┌────────┴─────────┐
                  │ Scheduler        │
                  │ Vercel Cron /    │
                  │ Netlify Schedule/│
                  │ GitHub Actions / │
                  │ cron-job.org     │
                  └──────────────────┘
```

### 構成のポイント

1. **単一 Next.js アプリに集約**（Webhook / Cron / 管理画面）。デプロイ対象が1つになり運用コストが最小。
2. **Cron は「5分ごと」に実行し、`next_reminder_at <= now()` のものを全件処理する。**
   「1時間ごとにちょうど起動する」設計にしない。理由：Cronが1回失敗しても次回で回収され、**通知漏れが構造的に発生しない**ため。
3. **通知の実送信は、DBで「確保（claim）」してから行う。** 確保は `FOR UPDATE SKIP LOCKED` + `reminders` の UNIQUE 制約で二重化を防ぐ。
4. **ドメインロジック（営業時間・次回通知時刻・エスカレーション判定）は副作用のない純粋関数**として切り出し、ユニットテストで固める。

## 5. 月額運用コスト

### 5-1. LINEメッセージ通数の見積り（最重要コスト要因）

LINE Messaging API の **push メッセージは課金対象**、**reply メッセージは無料**。
また **グループへの push は「グループ内の人数分」としてカウントされる**点に注意。

想定：社内グループ 5名 / 未返信が 1日あたり 5件発生 / 1件あたり平均 2回リマインド

```
1日の社内通知 push 数 = 5件 × 2回 = 10 push
グループ宛カウント     = 10 push × 5名 = 50通/日
月間                  = 50 × 30 = 1,500通/月
```

→ **LINE公式アカウント「フリープラン」（無料200通/月）では不足。**

| 対策 | 月額 | 備考 |
|------|------|------|
| (a) LINE公式アカウント **ライトプラン** | **¥5,000** | 5,000通/月。上記想定に収まる |
| (b) 社内通知を **個人宛 push** に限定（グループ不使用） | ¥0〜 | 担当者1名宛なら 10通/日 = 300通/月 → ライトプラン推奨 |
| (c) 社内通知を **Slack / Discord / LINE WORKS** に変更 | **¥0** | 通数課金なし。**コスト最適** |
| (d) 通知間隔を「2時間ごと」に設定 | 通数半減 | 本システムの設定機能で変更可 |

> 本システムは通知チャネルを差し替え可能に実装している（`NotificationChannel`）。
> **コスト最優先なら (c) Slack/Discord、LINEにこだわるなら (a) ライトプラン。**
> なお **LINE Notify は 2025年3月31日でサービス終了**しているため利用不可。

## 6. セキュリティ上の注意点

| # | リスク | 対策（本実装での対応） |
|---|--------|----------------------|
| 1 | **Webhookのなりすまし** — 第三者が偽の顧客メッセージを投入 | `x-line-signature` を **生のリクエストボディ**に対して HMAC-SHA256 検証。`crypto.timingSafeEqual` でタイミング攻撃を防止。検証失敗は 401 |
| 2 | **Cronエンドポイントの外部叩き** | `X-Cron-Secret` ヘッダの定数時間比較。未設定時は起動を拒否 |
| 3 | **個人情報（氏名・LINE ID・問い合わせ内容）の漏洩** | 管理画面は認証必須。全ページ `noindex`。ログにメッセージ本文を出さない（`redactText()`）。DBは TLS 接続必須（`sslmode=require`） |
| 4 | **アクセストークンの流出** | すべて環境変数。リポジトリにコミットしない（`.env*` を `.gitignore`）。`.env.example` のみ管理。定期ローテーション手順を `docs/06-operations.md` に記載 |
| 5 | **管理画面への不正ログイン** | scrypt によるパスワードハッシュ（ソルト付き）、HMAC署名付き HttpOnly / Secure / SameSite=Lax セッションCookie、ログイン試行のレート制限、役割ベース権限（ADMIN / MANAGER / STAFF） |
| 6 | **CSRF** | 状態変更API は同一オリジン検証（`Origin` ヘッダ）+ SameSite Cookie |
| 7 | **SQLインジェクション** | Prisma のパラメータ化クエリのみ使用。生SQLは行ロック取得部のみで、値は全てバインド |
| 8 | **社内LINEへの誤送信（顧客情報の外部流出）** | 通知先 `groupId` / `userId` は環境変数と管理画面で明示設定。テスト送信機能で事前確認 |
| 9 | **通知内容に機微情報が載る** | 通知本文のメッセージ抜粋は既定 60 文字でトリム。設定で「本文を含めない」も選択可 |
| 10 | **Webhookの再送による二重登録** | `webhook_events.webhook_event_id` に UNIQUE 制約。重複は 200 を返して無視 |
| 11 | **リプレイ攻撃** | Webhookイベントの `timestamp` が現在時刻から大きく乖離（既定 ±10分超）した場合は拒否 |
| 12 | **依存パッケージの脆弱性** | Dependabot / `npm audit` を CI に組み込む |
| 13 | **データ保持** | 退去済み顧客のメッセージは保持期間（既定 24ヶ月）経過後に削除するバッチを用意 |

## 7. この設計で「絶対に見逃さない」を担保する仕組み（要件の中核）

| 事故パターン | 防止策 |
|-------------|--------|
| **通知漏れ**：Cronが落ちていた / 実行に失敗した | ① Cronは「期限到来分を全件処理」する設計のため、遅延しても必ず配信される<br/>② `next_reminder_at` が閾値以上past のまま残っている会話を検知する **watchdog** が動作し、`要確認` に自動遷移＋管理者へ通知<br/>③ Cron自体の死活を外部監視（heartbeat）で検知 |
| **通知漏れ**：通知APIがエラーを返した | `reminders` に `FAILED` として記録し、指数バックオフで再試行。3回失敗で代替チャネル（冗長Webhook）へフォールバック |
| **通知漏れ**：顧客が短時間に連投し、毎回カウントがリセットされて永久に通知されない | `first_unreplied_at`（最初の未返信メッセージ時刻）を別途保持。<br/>**最新メッセージ基準のリマインドとは独立に、`first_unreplied_at` からの経過が上限（既定3時間）を超えたら強制通知**する |
| **二重通知**：Cronが多重起動した | ① `FOR UPDATE SKIP LOCKED` による行の排他確保<br/>② `reminders(conversation_id, dedupe_key)` の UNIQUE 制約<br/>③ 送信直前にトランザクション内で状態を再確認 |
| **二重通知**：複数担当が同時に操作 | 会話行の `version` による楽観ロック。競合時は 409 を返して再取得を促す |
| **返信済みなのに通知が続く** | 返信検知（管理画面送信 / 対応済み操作 / 取り込みAPI）時に `next_reminder_at = NULL` を同一トランザクションで確定。送信ワーカーは送信直前に `last_inbound_at > last_outbound_at` を再判定し、偽なら送信を中止 |
| **営業時間外に大量通知** | 営業時間・休業日を判定し、通知は次営業開始時刻へ**繰り延べ（スキップではない）** |
