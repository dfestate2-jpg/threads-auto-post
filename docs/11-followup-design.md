# 11. 自動追客管理システム — 設計

## 1. 中心にある考え方

追客管理の全体は、たった1本の式で決まる。

```
次回アクション日時 = ステータスになった時刻（statusSince） + そのステップの経過分数（offsetMinutes）
```

営業担当が次回追客日を入力しないのは、この式があるため。
「1日後 → 3日後 → 7日後 → 14日後 → 30日後」という指示書の追客リズムは、
`follow_up_rules` に並べた `offsetMinutes` の列としてそのまま表現されている。

判定ロジックは副作用のない関数として `src/lib/domain/followUp.ts` に置き、
DBやネットワークに触れずにテストできるようにしてある。

---

## 2. 状態遷移

```
                       顧客から返信
      ┌──────────────────────────────────────────┐
      │                                          │
      ▼                                          │
 新規反響 → 初回対応済 → ヒアリング済 → 物件提案中 ─┼→ 見積書待ち
                                        │        │       │
                                        ▼        │       ▼
                                  内見調整中 ─────┼→ 内見済 → 申込検討 → 申込済 → 成約
                                                  │
      各ステータスの最終ステップで反応が無ければ ──┘
                          ↓
                      返信なし ──30日──→ 休眠 ──60日/90日──→ 掘り起こしLINE
                          ↓
                        失注（人が選んだときだけ）
```

**重要な性質：どのステータスからも追客が途切れない。**
各ステータスの最終ステップは `transitionTo` を持つ自動遷移になっており、
反応が無いまま放置された顧客は必ず「返信なし」→「休眠」へ送られる。
失注になるのは、人が明示的に失注ボタンを押したときだけ。

### 自動で動くもの / 人が決めるもの

| 遷移 | 誰が |
|------|------|
| 新規反響 → 初回対応済 | 自動（LINEを送った時点） |
| 返信なし・休眠・保留 → 初回対応済 | 自動（顧客から返信が来た時点） |
| 返信なし → 休眠 | 自動（30日反応なし） |
| 物件提案中・見積書待ち・内見調整中・内見済・申込 | ボタン操作（＝営業行動の記録がそのままステータスになる） |
| 成約・失注・保留 | 人が明示的に選ぶ |

---

## 3. 追客ステップの進み方

```
statusSince = 2026-08-01 10:00  status = 返信なし  followUpStep = 0
   ↓ 次回アクション = 8/2 10:00「LINEで再アプローチ」

営業担当が「対応した」を押す
   ↓ followUpStep = 1
   ↓ 次回アクション = 8/4 10:00（= statusSince + 3日）

ステータスが変わる（例：物件を提案）
   ↓ statusSince = 今  followUpStep = 0
   ↓ 次回アクション = 提案から2日後
```

ステータスを指定した操作は「そのステータスの追客リズムを今から開始する」意味を持つ。
同じステータスを選び直した場合もリズムは再開する（再提案すれば、また2日後から数え直す）。

ステップを使い切った顧客は次回アクションが `null` になり、
今日の画面の **「追客ルール終了（要判断）」** に必ず現れる。黙って一覧から消えることはない。

## 4. 優先度の判定

`src/lib/domain/followUp.ts` の `computePriority` が決める。

| 材料 | 効果 |
|------|------|
| 手動で固定した優先度 | 最優先で採用 |
| 顧客からのLINEに未返信 | 無条件で **S** |
| ステータス | 新規反響・見積書待ち・内見調整中・申込検討・申込済 → 高め |
| 期限超過 | 一段上げる |
| 期限がまだ先 | 一段下げる（＝自動追客 C） |
| 追客ルールを消化しきった | A 以上に引き上げ（人の判断が要るため） |
| 引越し希望日が45日以内 | 一段上げる |
| 成約・失注 | C（追客対象外） |

将来 AI に置き換える場合も、この関数の入出力を保てば差し替えられる。

## 5. データベース

### customers（追加分）

| 列 | 意味 |
|----|------|
| `phone` / `email` | 連絡先 |
| `inquiredAt` / `inquirySource` | 問い合わせ日時・経路 |
| `desiredArea` / `desiredRent` / `moveInTiming` / `moveInBy` / `requirements` | 希望条件 |
| `status` / `statusSince` | 追客ステータスと、その開始時刻（ルールの起点） |
| `priority` / `priorityOverride` | 自動判定した優先度と、手動固定 |
| `lastContactAt` | 最終接触日時 |
| `nextActionAt` / `nextActionType` / `nextActionNote` | 次回アクション |
| `followUpStep` | 現在のステータス内で消化したステップ番号 |
| `autoFollowEnabled` | 自動追客の対象にするか |
| `contractedAt` / `contractAmount` / `lostAt` / `lostReason` | 成約・失注の記録 |
| `customFields` | 後から項目を足すための自由項目（JSON） |

`lineUserId` は **null を許容** に変更した。電話やポータル経由の反響は、LINE未連携のまま登録できる。

### follow_up_rules

ステータス × ステップの一意制約を持つ。`offsetMinutes` `actionType` `label` `templateKey` `notifyStaff` `transitionTo` `enabled`。

### follow_up_logs

追客履歴。`actionType` `source` `result` `note` `statusBefore` `statusAfter` `scheduledFor` `occurredAt` `dedupeKey`。
`scheduledFor` に「予定していた次回アクション日時」を残すため、期限に間に合ったかを後から分析できる。
`dedupeKey` は UNIQUE で、自動処理（休眠化・営業への通知）が二重に走らないことを物理的に保証する。

### message_templates

`key` `title` `body` `status` `sortOrder` `enabled`。本文には `{{name}} {{assignee}} {{area}} {{rent}} {{company}}` を差し込める。

## 6. 定期実行（`/api/cron/followups`・毎時）

1. **自動遷移** — 期限が来た `transitionTo` 付きルールを適用する（返信なし30日 → 休眠 など）
2. **営業への通知** — `notifyStaff` の段階（見積書待ち72時間など）を担当者と社内共通チャネルへ通知する
3. **優先度の引き直し** — 期限超過や引越し時期の接近は時間の経過だけで起きるため、誰も操作しなくても最新化する

いずれも「期限を過ぎた分をまとめて処理する」形にしてあるため、Cron が数回落ちても追客漏れにならない。
通知は送信前に `follow_up_logs` へ記録してから送るので、送信直後に落ちても二重には鳴らない。

## 7. 将来の拡張

| 項目 | 差し替える場所 |
|------|--------------|
| LINE文章のAI生成 | `messageTemplate.ts` の候補生成（候補を出す → 人が確認して送る、の経路は変えない） |
| 優先度のAI判定 | `computePriority`（入出力を保てば差し替え可能） |
| 追客リズムの学習 | `follow_up_rules` の `offsetMinutes` を書き換えるだけで全顧客に反映される |
| Lステップのタグ連携 | 既存の Webhook 受け口（`/api/line/relay`）から `recordFollowUpAction` を呼ぶ |
