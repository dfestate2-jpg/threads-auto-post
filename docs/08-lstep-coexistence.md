# 08. Lステップとの共存（Webhook転送）と、グループを使わない社内通知

## 前提となる制約

1. **LINE Messaging API の Webhook URL は 1チャネルに 1つしか設定できない。**
   Lステップを導入している時点で、その枠は Lステップが使っている。
2. **Lステップ運用下では、社内用のLINEグループにBotを入れる運用は取らない。**
   グループイベントは Lステップ の想定外であり、友だち管理を壊しうる。

この2つを前提に、**Lステップを一切止めない**構成を採る。

---

## 1. Webhook の受け口：Lステップの「Webhook転送」を使う

```
顧客 → LINE公式アカウント → Lステップ（正） ──転送──→ 本システム /api/line/relay
```

LINE Developers の Webhook URL は **Lステップのまま触らない**。
本システムが停止しても、Lステップの自動応答・シナリオ配信は影響を受けない。

> 逆向き（本システムが受けてLステップへ横流しする）にすると、
> **本システムの障害がそのままLステップの停止になる。** 採らない。

### Lステップ側の設定

1. 管理画面 左メニュー **「オプション機能申し込み」→「webhook機能」** から
   **「LINE Webhook転送（転送先数:1）」** を申し込む（プロプラン以上のオプション）
2. **「アカウント設定」→「外部連携設定」** タブで、転送先URLに本システムのURLを登録する

### 登録する転送先URL

```
https://<本システムのホスト>/api/line/relay?token=<LSTEP_RELAY_TOKEN>
```

`LSTEP_RELAY_TOKEN` は `openssl rand -hex 32` で生成し、環境変数に設定する。

> ⚠️ **この URL 自体が認証情報**になる。リポジトリにコミットせず、
> 共有はパスワード管理ツール経由で行う。漏れた場合はトークンを再生成して差し替える。

### なぜトークンが要るのか（署名だけで済まない理由）

LINEから直接届く Webhook は `x-line-signature` ヘッダーで真正性を検証できる。
**Lステップが転送するときにこのヘッダーを引き継ぐかは、公開資料では確定できない。**

そこで受け口 `/api/line/relay` は2経路を用意し、**強いほうを優先**する。

| 順位 | 経路 | 判定 |
|---|---|---|
| ① | `x-line-signature` があり検証も通る | 受理（暗号的に本物と確認できる） |
| ② | 署名が無く、転送用トークンが一致 | 受理 |
| — | 署名はあるが合わない | **拒否**（トークンが正しくても救済しない） |
| — | どちらも無い | 拒否 |

「署名はあるが合わない」を拒否するのは、鍵違いか偽装のどちらかであり、
**顧客の会話状態を書き換える入口では、通知漏れより誤受理のほうが重い**ため。

署名が引き継がれることが実運用で確認できたら、`LSTEP_RELAY_TOKEN` を外して
①だけの運用に切り替えてよい（そのほうが強い）。

### 転送されてくる形が違っても取りこぼさない

転送時に外側をどう包むかも資料で確定できないため、受け口は次をすべて受け付ける。

- `{ destination, events: [...] }`（LINE標準）
- `[ ...events ]` / イベント1件だけ
- `{ body: ... }` / `{ payload: ... }` / `{ data: ... }` / `{ webhook: ... }` / `{ original: ... }` で包まれたもの
- 上記が **JSON文字列** で入っているもの

それでも取り出せなかった場合、**必ず警告ログに「届いたデータの構造だけ」を残す**（値は出さない）。
静かに0件になって未返信を丸ごと取りこぼす、という事態を防ぐため。

### 導入直後にやる確認（重要）

1. `LSTEP_RELAY_DEBUG=1` を設定してデプロイする
2. 自分のスマホから公式LINEにメッセージを送る
3. サーバーログに `[line-relay] 受信` が出ることを確認する
   - `via: 'LINE_SIGNATURE'` → 署名が引き継がれている。トークンは外してよい
   - `via: 'RELAY_TOKEN'` → 署名は落ちている。トークンを外さないこと
   - `shape:` に `events` が含まれているか
4. 管理画面の未返信一覧に、そのメッセージが出ることを確認する
5. 確認できたら `LSTEP_RELAY_DEBUG` を外す

`[line-relay] イベントを取り出せませんでした` が出た場合は、`shape:` の内容を見て
`src/lib/line/relayPayload.ts` の `ENVELOPE_KEYS` に該当のキーを足す。

## 2. 社内通知：グループを使わず「担当者ごとの1対1」で送る

LINEグループが使えないため、**社内共通の宛先も個人宛の集合として表現する**。
本システムは宛先を種類ごとに扱うので、グループの代わりに
**担当者全員を個別の宛先として登録すれば同じ効果**になる（コード変更は不要）。

### 通知先の作り方

**「社内共通の通知先」に、通知を見せたい人を全員 `LINE_USER` で登録する。**
これがグループの代わりになる。

| 用途 | 登録先 | 種類 |
|---|---|---|
| 社内共通の通知先（＝グループの代わり） | 設定 → 通知チャネルに、営業・事務など**全員**を **`LINE_USER` / 用途 `DEFAULT_GROUP`** で登録 | 全員へ個別push |
| 顧客ごとの担当者 | スタッフ管理で各担当者に **LINEユーザーID** を登録 | 個別push |
| 責任者・管理者へのエスカレーション | スタッフの役割（MANAGER / ADMIN）とエスカレーション設定 | 個別push |

### LINEグループを通知先にする場合

社内通知チャネル（チャネル②）は**Lステップと無関係**なので、
グループにBotを招待して、そのグループを通知先にできる。

```
1. LINE Official Account Manager（チャネル②）
   → 設定 → アカウント設定 → 「グループ・複数人トークへの参加」を許可する
2. 社内のLINEグループにこのBotを招待する
3. Botが「通知先ID」を返信するので、それをコピーする
4. 管理画面 → 設定 → 通知チャネル に
   種類「LINEグループ」・用途「社内共通」で登録する
```

グループIDは画面のどこにも表示されないため、**招待時にBotが本人へ返信して伝える**。
あとから確認したい場合は、そのトークで「通知先ID」と送れば再度返す。

| | グループ | 個人宛（複数登録） |
|---|---|---|
| 消費通数 | 人数分 | 人数分（**同じ**） |
| 「対応済み」ボタン | 使える | 使える |
| 通知の見え方 | 1か所に集まる。会話もできる | 各自のトークに届く |
| 担当者だけに絞る | できない | できる |
| 新しく入った人 | グループに入れるだけ | 1人ずつ登録が必要 |

**どちらでも動く。**運用が楽なほうを選べばよい。両方を併用することもできる
（グループ＋責任者個人、など）。

### 担当者が決まっていても、全員に同報する

**担当者以外（事務など）が返信することがあるため、既定では担当者と社内共通の通知先の両方へ送る。**

担当者にしか届かないと、担当者が外出中・接客中の案件を他の人が拾えない。
これは「返信されないまま放置される」という、このシステムが防ごうとしている状態そのものになる。

| 設定 | 挙動 |
|---|---|
| **`担当者が決まっていても、社内共通の通知先へ同報する`（既定ON）** | 担当者 ＋ 社内共通の通知先の全員 |
| OFF | 担当者だけ（担当者未設定のときのみ社内共通へ） |

設定 → 全般 で切り替えられる。

- 担当者が社内共通の通知先にも登録されていても、**二重には送られない**（宛先は重複排除される）
- 通知本文には `担当者：〇〇` が必ず入るので、**誰が一次対応すべきかは全員に分かる**
- 誰が押しても「対応済み」になる。**事務の方が返信してタップしてもリマインドは止まる**
- 一方が押した後に別の人が押しても「既に対応済みです」と返るだけで、二重処理にはならない

### 通数について

同報する人数分が消費される（グループ宛pushも人数分カウントなので、グループが使えた場合と同じ）。

- 5人へ同報、未返信5件/日、平均2回リマインド → 月およそ1,500通
- ライトプラン 5,000通/月 に対して**3割程度**

通数を抑えたい場合は、同報をOFFにするか、社内共通の通知先の人数を絞る。

### どのLINEアカウントから送るか

2案を検討し、**案②（専用チャネル新設）を採用**した。

案①は「Lステップが止まる」リスクは無いが、一斉配信の除外タグを毎回外し忘れない、
という人間の運用に依存する。本システムを作る動機が「人間の運用が回らないから自動化する」
である以上、同種のリスクを新たに持ち込むのは筋が通らない。

#### 案①（不採用）顧客対応チャネル（Lステップ管理下）をそのまま使う — 追加費用 0円

営業マンが公式LINEを友だち追加し、そのユーザーIDへ push する。

- 追加のアカウント・費用が不要
- ただし **Lステップの友だちリストに営業マンが混ざる**
- Lステップの一斉配信・シナリオ配信で**営業マンに営業メッセージが誤爆する**リスク
  → Lステップ側で「社内」タグを付け、全配信で除外する運用が必須

#### 案②【採用】社内通知専用のLINE公式アカウントを新規作成 — 月5,500円〜

Lステップを紐づけない別チャネルを作り、営業マンだけが友だち追加する。

- Lステップと**完全に分離**。友だちリストも配信も一切混ざらない
- 誤爆リスクがゼロ
- 「対応済みにする」ボタンのタップ（postback）もこちらで受ける
  → `LINE_NOTIFY_CHANNEL_ACCESS_TOKEN` と `LINE_NOTIFY_CHANNEL_SECRET` を設定し、
    そのチャネルの Webhook URL を `/api/line/webhook` に向ける
- 社内通知は月1,500通程度 → フリープラン（200通/月）では足りず、
  **ライトプラン（5,000通/月）が必要**

> 顧客対応チャネル①の Webhook URL は **Lステップのまま**であることに注意。
> チャネル②の Webhook URL だけを本システムに向ける。両者は別チャネルなので競合しない。

### チャネル②のイベントは顧客対応の対象にしない

チャネル②に届くメッセージ・友だち追加は**すべて社内の人間**である。
これを素通しすると、社内の人が「未返信の顧客」として一覧に並び、
本人宛にリマインドが鳴り続ける。

そこで、署名がチャネル②のものだったイベントは顧客対応から完全に外し、
**受け付けるのは「担当者の連携コード」と「対応済みボタンのタップ」だけ**にしている。

### 担当者のLINEユーザーIDは「連携コード」で登録する

LINEユーザーIDは `U` + 32桁で、管理画面へ書き写すと必ず打ち間違える。
間違ったIDを登録すると**通知が別人に飛ぶか、誰にも届かない**——どちらも見逃しに直結する。

```
1. 管理画面 → 設定 → 担当者 → その人の行の「連携コード発行」を押す
2. 画面に ABCD-2345 のようなコードが出る（有効期限24時間）
3. 本人に伝え、社内通知Botのトークに送ってもらう
4. 「「〇〇」として登録しました」と返ってきたら完了
```

安全策：

- コードは**ハッシュでしか保存しない**（DBが漏れてもコードは復元できない）
- **使い捨て**。一度使われたコードは再利用できない
- **24時間で失効**
- 再発行すると**前のコードは無効**になる（有効なのは常に最後の1本）
- 既に他の担当者に紐づいているLINEアカウントは**奪えない**
- 読み違えやすい `I / L / O / 0 / 1` を除いた8文字
- コードを含まない発言（雑談・スタンプ）には**何も返さない**

> 返信（reply）は無料なので、この一連のやり取りでメッセージ通数は消費しない。

#### 案②（参考）

### 「対応済みにする」ボタンとの関係

社内通知先が LINE であれば、通知の直下に `✅ 対応済みにする` ボタンが付く。
グループが無くても、**個人宛の通知にそのまま付く**（仕様上の違いはない）。

タップを受け付けるのは、社内通知グループまたは
**担当者としてLINEユーザーIDを登録済みのアカウント**のみ。
グループを使わない構成では後者だけが有効になるため、
**通知を受け取る営業マンは全員スタッフ登録が必要**。詳細は [07](./07-line-reply-detection.md)。
