# 07. 担当者の返信をどう検知するか（最重要の制約と対策）

## 結論

**LINE Messaging API の標準機能では、「担当者が LINE Official Account Manager のチャット画面から
送った返信」をシステム側で自動検知することはできない。**

これは実装の工夫では回避できない、LINE 側の仕様上の制約である。
依頼の基本フロー「6. 担当者が公式LINEから返信したら『対応済み』と判定」を
**そのまま実現するには、返信の出口を設計で決める必要がある。**

## 制約の内容

LINE Messaging API の Webhook が配信するイベントは、**顧客 → 公式アカウント方向のみ**。

配信されるイベント：
`message` / `unsend` / `follow` / `unfollow` / `join` / `leave` / `memberJoined` /
`memberLeft` / `postback` / `videoPlayComplete` / `beacon` / `accountLink` / `things` / `membership`

**公式アカウントが送信したメッセージに対応するイベントは存在しない。**
Messaging API から `push` / `reply` で送った場合も、LINE Official Account Manager の
チャット画面から手で送った場合も、いずれも Webhook には流れてこない。

## 本システムの対策：5つの検知経路

| 経路 | 確実性 | 対応済み判定 | 使いどころ |
|------|-------|-------------|-----------|
| **A. 管理画面から返信する** | ◎ 100% 自動 | 送信成功と同時に確定 | 管理画面を業務の入口にできる場合 |
| **B. 社内LINE通知の「対応済みにする」ボタン** | ○ タップ1回 | タップで確定 | **公式LINEのチャット画面から返信したい場合の推奨経路** |
| **C. 管理画面の「対応済みにする」ボタン** | ○ 手動 | ボタン操作で確定 | 社内通知がSlack等でボタンを使えないときの補完 |
| **D. 取り込みAPI `POST /api/ingest/outbound`** | ○ 自動（要外部連携） | API 受信で確定 | iPaaS / CRM / Lステップ / LINE Module Channel と連携できる場合 |
| **E. フェイルセーフ（通知を止めない）** | ◎ | — | B〜D が実行されなくても通知が続くため、必ず誰かが気付く |

### A. 管理画面から返信する（推奨）

顧客詳細画面の一番上に返信欄を置いてある。ここから送ると：

1. Messaging API の `push` で顧客の LINE に届く
2. **送信が成功した場合にのみ** `messages` に OUTBOUND を記録し、`conversations` を `REPLIED` に遷移
3. `nextReminderAt` を同一トランザクションで NULL にしてリマインドを停止

**返信の出口を管理画面に一本化すれば、依頼の要件は完全自動で満たされる。**
運用ルールとして「顧客への返信は管理画面から行う」と決めるのが、最もコストが低く確実。

> 送信に失敗した場合は `502` を返し、**リマインドは止めない**。
> 「返信できていないのに通知が止まる」ほうが事故として重大なため。

### B. 社内LINE通知の「対応済みにする」ボタン（公式LINEから返信する運用の推奨経路）

社内通知先を **LINE**（担当者個人 or 社内グループ）にしている場合、
リマインド通知の直下に `✅ 対応済みにする` ボタンが付く。

```
⚠️ 未返信 1時間20分
山田太郎 様（担当：内田翔太）
『内見の件ですが、来週の土曜日は…』

返信したら下のボタンをタップしてください。

┌─────────────────────────┐
│ 山田太郎 様への操作              │
│      ✅ 対応済みにする              │
│      🙋 自分が担当にする             │
└─────────────────────────┘
```

この文面は **設定 → 全体設定 → リマインドの文面** から編集できる。
`{顧客名}` `{担当者}` `{経過時間}` などを差し込む形式で、編集中の見本がその場に出る。
空にすると既定の文面に戻る（空のまま保存して本文が空の通知が飛ぶ、という事故を防ぐため）。
既定では管理画面のURLを入れていない。毎回URLが並ぶとトークが読みにくく、
グループのノートに貼れば足りるため。必要なら `{URL}` を足せば戻せる。
ボタンは文面に関係なく常に付く。

読むのはスマホのLINEで、しかも営業中の担当者。情報を並べるほど読み飛ばされるため、
**次の行動を変えないものは載せない**。載せるのは
「誰が・どれだけ待っているか・何の話か・自分の担当か」の4つだけ。
落とした情報（リマインド回数など）は管理画面で見られる。

経過時間は **最初の未返信から** の一本に統一している。顧客が追加メッセージを送るたびに
短い数字が出ると、連投されている案件ほど軽く見えて後回しになる。実際は逆に急ぐべきもの。

放置が長引くほど1行目の印を強くする。

| 状態 | 1行目 |
|---|---|
| 通常 | `⚠️ 未返信 1時間20分` |
| 連投中 | `⚠️ 未返信 3時間15分（メッセージ連投中）` |
| エスカレーション | `🚨 未返信 3時間20分／責任者にも通知` |
| 24時間超 | `🚨🚨 未返信 1日2時間／管理者にも通知` |

ボタンは本文とは別の吹き出しで出る。通知が何件も溜まるとボタンだけ見ても誰のものか
分からず、**別の顧客のボタンを押す**事故が起きるため、宛先の顧客名を必ず上に出す。

営業担当は **公式LINEのチャット画面でいつもどおり返信し、社内LINEに来た通知をタップするだけ**。
管理画面を開く必要がないため、工数はほぼ増えない。

仕組みと安全策：

- ボタンのデータは HMAC 署名付き（`src/lib/line/quickAction.ts`）。改ざんされたタップは無視する
- 署名に加えて **発信元も検証する**。社内通知グループ、または担当者として登録済みの LINE アカウントからのタップのみ受け付ける
- データには「その未返信サイクルの起点（`firstUnrepliedAt`）」を埋めてある。
  **古い通知のボタンを押しても、その後に届いた新しい未返信は閉じられない**
  （「昨日の通知をスクロールして押したら今朝の問い合わせが消えた」という最悪の見逃しを構造的に防ぐ）
- 既に対応済みの案件を押した場合、複数人が同時に押した場合も二重処理にはならず、その旨を返信する
- 押し忘れてもリマインドは鳴り続ける（＝ 見逃しにはならない）

#### 「🙋 自分が担当にする」

同じ通知に並ぶもう1つのボタン。押した本人がその顧客の担当者になる。

担当者の割り当ては本来 管理画面 → 顧客詳細 でしか行えず、通知を見た流れで決められない。
それだと「後で入れよう」で未設定のまま残りやすいため、通知の場で完結させる。
ボタンは本文と同じ push にまとめて載るので、**消費通数は増えない**。

- 押した人が担当者として未登録の場合は割り当てず、連携コードでの登録を促す
  （誰に割り当てるかを推測しない）
- **未返信サイクルの一致はあえて見ない。** 担当者は会話ではなく顧客単位の属性であり、
  古い通知から担当を引き受けるのは正当な操作だから。
  取り違えに気づけるよう、応答には必ず顧客名と担当者名を出す
- **担当を引き受けても未返信は閉じない。** リマインドはそのまま続く
  （「担当が決まった」と「返信した」は別のことなので、混ぜると見逃しになる）
- 署名の対象に操作種別が入っているため、担当割当のデータを「対応済み」に化けさせることはできない

> ⚠️ 社内通知Botを顧客対応とは**別のLINEチャネル**で運用する場合、
> タップ（postback）はそのチャネルの Webhook に届く。
> `LINE_NOTIFY_CHANNEL_SECRET` を設定すると両方のチャネル署名を受理できる。

### C. 管理画面で手動で「対応済み」にする

「LINE公式Managerで返信済み → 対応済みにする」ボタンを用意している。
押すと `manual_resolution` という OUTBOUND レコードが1件残るため、
状態機械の一貫性が保たれ、かつ「誰がいつ対応済みにしたか」が監査ログに残る。

運用でこれを併用する場合は、**押し忘れが唯一のリスク**になる。
押し忘れても通知は続くだけなので「見逃す」ことはないが、不要な通知が出る。

### D. 取り込みAPI

外部システムが担当者の返信を検知できる環境であれば、そこから POST してもらう。

```bash
curl -X POST https://<host>/api/ingest/outbound \
  -H "x-ingest-secret: $INGEST_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"lineUserId":"Uxxxx","text":"ご連絡ありがとうございます"}'
```

`INGEST_SECRET` が未設定なら `404` を返して無効化されるため、使わない場合は設定しないこと。

なお LINE Webhook のハンドラには `send` / `sendMessage` イベントの取り込み口も実装済みで、
そうしたイベントを受け取れる環境（LINE Module Channel 等）ではコード変更なしに自動判定できる。

### E. フェイルセーフ

B〜D のいずれも行われなかった場合、システムは「まだ返信されていない」と判断し**通知を出し続ける**。
不要な通知は出るが、**「未返信を見逃す」ことは絶対に起きない**。
これは依頼の最重要要件に沿った意図的な設計判断である。

## 推奨する運用

### 運用パターン① 公式LINEから返信する（営業担当の工数を増やさない）

```
1. 顧客からのLINEには、いつもどおり公式LINEのチャット画面で返信する
2. 社内LINEに届いたリマインド通知の「✅ 対応済みにする」をタップする  ← タップ1回
3. 押し忘れても通知は鳴り続けるので、見逃しにはならない
```

社内通知先を LINE にする必要がある（`INTERNAL_LINE_GROUP_ID`、または担当者の LINE ユーザーIDを登録）。
Slack など Webhook 宛先にはボタンが出ないため、その場合は本文のリンクから管理画面で操作する。

### 運用パターン② 管理画面から返信する（完全自動）

```
1. 顧客からのLINEは管理画面の一覧で確認する
2. 返信は必ず管理画面の返信欄から送る          ← これだけで完全自動になる
3. どうしてもLINE公式Managerから返信した場合は、
   管理画面で「対応済みにする」を押す
```

どちらのパターンでも「未返信の見逃し」は起きない。違いは**押し忘れによる余分な通知が出るかどうか**だけ。

導入時に社内へ周知すべきは 2 の1行だけ。
LINE Official Account Manager を併用したい場合は、`INGEST_SECRET` を使った C の連携を検討する。

## 参考：管理画面から返信する場合のメッセージ通数

`push` メッセージは LINE公式アカウントの無料メッセージ通数を消費する（`reply` は無料）。
本システムは replyToken の有効期限（約1分）内に管理画面の操作が完結しないため `push` を使用している。

顧客への返信 30通/日 = 900通/月。フリープラン（200通/月）では不足するため、
**ライトプラン（¥5,000/月・5,000通）以上を想定しておくこと。**
詳細は [`01-requirements.md` の月額運用コスト](./01-requirements.md#5-月額運用コスト) を参照。

## まとめ通知（2回目以降）

問い合わせが多いと1件1通では社内LINEが埋まり、**かえって見落とす。**
そこで **初回だけ個別（ボタン付き）、2回目以降は1通にまとめる**。
設定「2回目以降のリマインドを1通にまとめる」で切り替えられる（既定は有効）。

```
⚠️ 未返信 3件（継続中）

🚨🚨 山田太郎 様 1日2時間（担当：内田）
🚨 佐藤花子 様 6時間（担当：未設定）
⚠️ 鈴木一郎 様 2時間（担当：舛谷）

対応済みにするには一覧から開いてください。
```

### まとめても取りこぼさないための作り

- **宛先ごとにまとめる。** 会話によって宛先は違う（担当者の個人LINE、社内グループ…）ので、
  全部を1通にして全員へ送ると、他人の担当顧客が個人LINEに流れる。
  「その宛先が本来受け取るはずだった分」だけを1通にする
- **記録と次回予定は1件ずつ確定する。** まとめ送信の結果を会話ごとに割り戻し、
  ひとつでも届いた宛先があれば送信成功として予定を進める。全滅した会話は
  個別の本文で予備送信したうえで再試行に回す
- **エスカレーションと保険通知（連投中）はまとめない。** 「重い」ことを伝える通知なので、
  埋もれさせてはいけない。ボタンも付いたまま
- **まとめ通知にボタンは付けない。** 宛先の顧客が1人に定まらないボタンは押し間違いを生み、
  「対応していない案件を対応済みにする」という一番まずい事故になる

`scripts/e2e-check.ts` の ⑯ で、初回が個別・2回目が1通・件数と予定が1件ずつ進むこと・
返信済みが翌回のまとめから外れることを実DBで確認している。
