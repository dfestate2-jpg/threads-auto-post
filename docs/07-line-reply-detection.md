# 07. 担当者の返信をどう検知するか（最重要の制約と対策）

## 結論

**LINE Messaging API の標準機能では、「担当者が LINE Official Account Manager のチャット画面から
送った返信」をシステム側で自動検知することはできない。**

これは実装の工夫では回避できない、LINE 側の仕様上の制約である。
依頼の基本フロー「6. 担当者が公式LINEから返信したら『対応済み』と判定」を
**そのまま実現するには、返信の出口を設計で決める必要がある。**

## 制約の内容

LINE Messaging API の Webhook が配信するイベントは、**顧客 → 公式アカウント方向のみ**。

配信されるイベント：
`message` / `unsend` / `follow` / `unfollow` / `join` / `leave` / `memberJoined` /
`memberLeft` / `postback` / `videoPlayComplete` / `beacon` / `accountLink` / `things` / `membership`

**公式アカウントが送信したメッセージに対応するイベントは存在しない。**
Messaging API から `push` / `reply` で送った場合も、LINE Official Account Manager の
チャット画面から手で送った場合も、いずれも Webhook には流れてこない。

## 本システムの対策：4つの検知経路

| 経路 | 確実性 | 対応済み判定 | 使いどころ |
|------|-------|-------------|-----------|
| **A. 管理画面から返信する** | ◎ 100% 自動 | 送信成功と同時に確定 | **推奨。標準の運用にする** |
| **B. 管理画面の「対応済みにする」ボタン** | ○ 手動 | ボタン操作で確定 | LINE Manager で返信してしまったときの補完 |
| **C. 取り込みAPI `POST /api/ingest/outbound`** | ○ 自動（要外部連携） | API 受信で確定 | iPaaS / CRM / LINE Module Channel と連携できる場合 |
| **D. フェイルセーフ（通知を止めない）** | ◎ | — | B/C が実行されなくても通知が続くため、必ず誰かが気付く |

### A. 管理画面から返信する（推奨）

顧客詳細画面の一番上に返信欄を置いてある。ここから送ると：

1. Messaging API の `push` で顧客の LINE に届く
2. **送信が成功した場合にのみ** `messages` に OUTBOUND を記録し、`conversations` を `REPLIED` に遷移
3. `nextReminderAt` を同一トランザクションで NULL にしてリマインドを停止

**返信の出口を管理画面に一本化すれば、依頼の要件は完全自動で満たされる。**
運用ルールとして「顧客への返信は管理画面から行う」と決めるのが、最もコストが低く確実。

> 送信に失敗した場合は `502` を返し、**リマインドは止めない**。
> 「返信できていないのに通知が止まる」ほうが事故として重大なため。

### B. 手動で「対応済み」にする

「LINE公式Managerで返信済み → 対応済みにする」ボタンを用意している。
押すと `manual_resolution` という OUTBOUND レコードが1件残るため、
状態機械の一貫性が保たれ、かつ「誰がいつ対応済みにしたか」が監査ログに残る。

運用でこれを併用する場合は、**押し忘れが唯一のリスク**になる。
押し忘れても通知は続くだけなので「見逃す」ことはないが、不要な通知が出る。

### C. 取り込みAPI

外部システムが担当者の返信を検知できる環境であれば、そこから POST してもらう。

```bash
curl -X POST https://<host>/api/ingest/outbound \
  -H "x-ingest-secret: $INGEST_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"lineUserId":"Uxxxx","text":"ご連絡ありがとうございます"}'
```

`INGEST_SECRET` が未設定なら `404` を返して無効化されるため、使わない場合は設定しないこと。

なお LINE Webhook のハンドラには `send` / `sendMessage` イベントの取り込み口も実装済みで、
そうしたイベントを受け取れる環境（LINE Module Channel 等）ではコード変更なしに自動判定できる。

### D. フェイルセーフ

B も C も行われなかった場合、システムは「まだ返信されていない」と判断し**通知を出し続ける**。
不要な通知は出るが、**「未返信を見逃す」ことは絶対に起きない**。
これは依頼の最重要要件に沿った意図的な設計判断である。

## 推奨する運用

```
1. 顧客からのLINEは管理画面の一覧で確認する
2. 返信は必ず管理画面の返信欄から送る          ← これだけで完全自動になる
3. どうしてもLINE公式Managerから返信した場合は、
   管理画面で「対応済みにする」を押す
```

導入時に社内へ周知すべきは 2 の1行だけ。
LINE Official Account Manager を併用したい場合は、`INGEST_SECRET` を使った C の連携を検討する。

## 参考：管理画面から返信する場合のメッセージ通数

`push` メッセージは LINE公式アカウントの無料メッセージ通数を消費する（`reply` は無料）。
本システムは replyToken の有効期限（約1分）内に管理画面の操作が完結しないため `push` を使用している。

顧客への返信 30通/日 = 900通/月。フリープラン（200通/月）では不足するため、
**ライトプラン（¥5,000/月・5,000通）以上を想定しておくこと。**
詳細は [`01-requirements.md` の月額運用コスト](./01-requirements.md#5-月額運用コスト) を参照。
