# Company OS — 会社経営を一元管理する

## 1. これは何か

会社の立ち上げから経営までを 1 か所で管理するための画面群です。
既存の追客管理システム／リマインドシステムとは**独立**していて、
同じデータベースを共有しますが、テーブルは `co_` 接頭辞で完全に分かれています。
片方を止めても、もう片方は動きます。

目的は「情報を保存すること」ではなく、**経営者が次に何をすべきか分かること**です。
そのため、どの画面も次の循環のどこかを担っています。

```
データを入力 → 情報を整理 → 状況を分析 → 問題を発見
    → 優先順位を決定 → タスク化 → 実行 → 結果を記録
```

入口は `/company-os`。業務システムポータル（`/portal`）にもカードが並びます。

## 3. データ構造

すべて `prisma/schema.prisma` の末尾にあります。テーブル名は `co_*`。

```
CoCompany ─┬─ CoMember ──── (assignee) ─┐
           ├─ CoShareholder             │
           ├─ CoProject ─┬─ CoMilestone │
           │             └─ CoTask ─────┤─ CoTaskDependency（先行／後続）
           │                            ├─ CoChecklistItem
           │                            └─ CoComment
           ├─ CoIssue ──── CoTask（対策タスク）/ CoDecision
           ├─ CoDecision ── CoDecisionRevision（変更履歴）
           ├─ CoQuestion ── CoDecision（決まったとき）
           ├─ CoMeeting ── CoTask / CoIssue / CoDecision / CoQuestion
           ├─ CoObjective（経営目標・KPI）
           └─ CoDocument（重要書類・期限）
```

設計上の判断:

- **会社は複数持てる**。買収した会社を別レコードとして並べ、上部で切り替えます。
  見ている会社は Cookie（`co_company`）に保持します。URL のクエリで渡すと、
  書き換えるだけで他社のデータに触れられてしまうためです。
- **メンバーはログインアカウントと分離**。アカウントを持たない共同創業者や外部の担当も
  タスクの担当者にできます（`CoMember.userId` は任意）。
- **削除しても仕事は消えない**。担当者やプロジェクトを消すと、参照は外れますが
  タスク自体は残ります（`onDelete: SetNull`）。引き継ぎができなくなるためです。
- **公開範囲**（`CoVisibility`）を課題・決定・会議・書類に持たせています。
  経営者だけが見る情報は、一覧の SQL の時点で落とします。

## 4. 優先順位の決め方

`src/lib/company-os/priority.ts`。期限順ではなく、次の要素を 1 つの点数にまとめます。

| 要素 | 効き方 |
| --- | --- |
| 優先度（最優先/高/中/低） | 40 / 25 / 12 / 4 点 |
| 期限 | 超過は 40 点＋1 日ごとに 2 点（10 日で頭打ち）。今日 32 点、明日 24 点 |
| 売上への影響（0〜3） | ×6 点 |
| リスク（0〜3） | ×6 点 |
| 他タスクを止めている数 | ×5 点（4 件で頭打ち） |
| プロジェクトの状態 | 進行中 +3、最優先 +5、遅延 +5 |
| 着手済み | +4（並行して抱えるほど会社全体は遅くなる） |
| 保留 | −20 |
| 先行タスク待ち | 点数を 0.4 倍（今日は着手できないため） |

点数は 70/45/22 を境に「最優先・高・中・低」に落とします。
**算出理由は必ず言葉で返します**（例: 「48日超過／リスクがある／他の1件を止めている」）。
点数だけでは経営者は納得できないためです。

ダッシュボードの「今日の最重要 TOP5」は、この点数から先行待ちのタスクを除いて選びます。

Phase3 で言語モデルに置き換える場合も、入力（`TaskSignals`）と出力（`Scored`）の形を
保てば画面側は変更不要です。

## 5. AI経営アシスタント（Phase1 はルールベース）

`src/lib/company-os/advisor.ts`。

- 会社のデータを 1 つの `CompanySnapshot` にまとめ（`services/companyOs/snapshot.ts`）、
  そこから「いま止まっているもの」を検出します。
- 検出するもの: 期限超過、重大な課題、担当者のいない課題、対策の無い課題、
  遅延／遅れ気味のプロジェクト、担当者未定のタスク、期限切れの未決事項、
  着手できないタスクの滞留、期限が近い書類、意思決定の記録漏れ、
  設立の進捗、キャッシュの残月数。
- 質問への回答は意図（今日/課題/期限/プロジェクト/決定/未決/数値/まとめ）を判定して答えます。

**外部には何も送信していません。** Phase3 で言語モデルに置き換えるときも、
モデルに見せる範囲＝`CompanySnapshot` の範囲であり、権限による絞り込みもここで行います。

## 6. 議事録の自動仕分け

`src/lib/company-os/minutes.ts`。

`## 決定事項` `## タスク` `## 課題` `## 未決事項` のような見出し、または
行頭の `決定：` `タスク：` から種類を判定し、`担当:山田` `期限:10/15` を抜き出します。

**抽出結果をそのまま保存はしません。** 必ず一覧で見せ、種類の付け替えと取捨選択を
してから登録します（誤読を黙って台帳に残さないため）。担当者は、同じ名前のメンバーが
登録されている場合だけ自動で割り当てます。

## 7. テンプレート

`src/lib/company-os/templates.ts` に定義（データのみ）。

- **会社立ち上げ**（45 タスク・4 マイルストーン）:
  会社設計 → 登記 → 法人口座 → 会計 → 営業資料 → 商品完成 → 初回営業 → 初回契約
  を依存関係でつないであります。
- **会社買収**（16 タスク・3 マイルストーン）:
  DD（登記・財務・契約・システム）→ 譲渡契約 → 買収後の引き継ぎ。

タスクには `templateKey`（会社ごとに一意）を持たせているため、**押し直しても増えません**。
テンプレートの依存関係は起動時ではなくテスト（`tests/companyOsTemplates.test.ts`）と
実行前の `validateTemplate` で検証しており、循環したまま流し込まれることはありません。

## 8. 権限

会社内の役割は `CoMember.role`（OWNER / ADMIN / MANAGER / MEMBER / VIEWER）。
メンバー未登録の人は、ログインアカウントの役割から引き継ぎます
（ADMIN→ADMIN、MANAGER→MANAGER、STAFF→MEMBER）。導入初日に誰も入れない状態を避けるためです。

| 操作 | 必要な権限 |
| --- | --- |
| 閲覧 | 全員（公開範囲による絞り込みあり） |
| タスク・課題・決定などの作成／編集／削除 | MEMBER 以上 |
| 会社情報・メンバー・株主の変更 | ADMIN 以上 |

API は画面と同じ判定を通ります（`services/companyOs/context.ts`）。
状態を変える API はすべて同一オリジンからのみ受け付けます（既存の `assertSameOrigin`）。

## 9. 経営数値について

売上・経費・キャッシュ残高・商談数・顧客数・契約数は、財務モジュールと営業CRM（Phase2）が
入るまで自動集計できません。ダミーを表示するとダッシュボード全体が信用されなくなるため、
**KPI（`CoObjective.metricKey`）に実データとして保存し、KPI 画面から手で更新する**方式にしています。
Phase2 では同じ行を自動更新すればよく、画面の変更は不要です。

## 10. 構成

```
src/lib/company-os/          … DBに依存しない純粋なロジック（テスト対象）
  priority.ts    優先順位エンジン
  advisor.ts     経営診断と質問応答
  minutes.ts     議事録の仕分け
  templates.ts   プロジェクトテンプレート
  progress.ts    進捗・遅延判定
  access.ts      権限・公開範囲
  date.ts        期限の扱い（タイムゾーン込み）
  labels.ts      表示ラベルと配色
  formSpecs.ts   入力項目の定義
  nav.ts         サイドバー
  metrics.ts     経営数値の定義

src/lib/services/companyOs/  … DB操作（Prisma）
src/app/company-os/          … 画面（Server Component）
src/app/api/company-os/      … API（Route Handler）
src/components/company-os/   … 表示部品・クライアント側の操作
```

API は `[resource]` の汎用ルートに集約し、リソース定義（`services/companyOs/resources.ts`）を
引いて処理します。同じ検証と権限チェックを何度も書かずに済ませるためです。

## 11. ローカルでの動かし方

```bash
# 1. PostgreSQL を用意し、.env に DATABASE_URL / DIRECT_URL / SESSION_SECRET / CRON_SECRET を設定
npm install
npm run prisma:migrate        # マイグレーション適用

# 2. 動作確認用のデータを入れる（本番DBでは実行しないこと）
npm run seed:company-os

# 3. 起動
npm run dev
# http://localhost:3000/login → admin@example.com / demo-password-1234
# → http://localhost:3000/company-os
```

デモデータを入れない場合は、ログイン後 `/company-os` を開くと会社の登録画面に進み、
「会社立ち上げテンプレートを作成する」を選んだ状態で登録すれば、その場でタスクが並びます。

既に運用中の環境では、ポータルの初期カードが投入済みのため Company OS のカードは
自動では追加されません。`/portal/admin` から「Company OS」（URL: `/company-os`）を
登録してください。
