# 05. 判定ロジック仕様

実装：`src/lib/guarantee/engine.ts` ／ 会社定義：`src/lib/guarantee/companies.ts`
テスト：`tests/guarantee.test.ts`（28ケース）

---

## 1. 基本構造

```
　　スコア = 100 ＋ Σ（各ルールの点数 × その会社がその情報を見られる度合い）
```

**この「× その会社がその情報を見られる度合い」が本システムの中核**です。
同じ「3年前に自己破産」という事実に対して、

| 会社 | CIC/JICC weight | 減点 | 結果 |
|---|:---:|---:|:---:|
| エポス | 1.0 | −100 | **×** |
| エルズサポート | 1.0（JICC） | −100 | **×** |
| Casa | 0.5（JICC・実務は自社DB優先） | −50 | **△** |
| 全保連 | 0.5（JICC加盟が未確認） | −50 | **△** |
| 日本セーフティー | 0 | **0** | **○** |

が**自動的に**導かれます。会社ごとに if 文を書いていません。
会社定義（`companies.ts`）を書き換えるだけで判定が変わります。

### スコア → 判定の写像

| 判定 | スコア | 意味 |
|:---:|---|---|
| ◎ | 90〜100 | 通過可能性かなり高い |
| ○ | 70〜89 | 通過可能性あり |
| △ | 45〜69 | 注意・審査次第 |
| × | 0〜44 | 通過可能性低い |
| ？ | ― | 判定に必要な情報が足りない |

**ハードリジェクト**（代位弁済歴、現在延滞中、直近の債務整理など）に該当した場合は、
他にどれだけプラス材料があってもスコアを 20 以下に固定します。
補強材料で覆せない事象を、補強材料で覆せるように見せないためです。

## 2. ルール一覧

### ① 当該保証会社での利用歴（channel: `own`, weight 常に 1.0）

自社DBには保有期限がありません。**最も重いルール群です。**

| ruleId | 条件 | 点数 |
|---|---|---:|
| `own_legal` | その社で訴訟・明渡しに至った | **ハードリジェクト** |
| `own_subrogation` | その社で代位弁済に至った | **ハードリジェクト** |
| `own_late_serious` | その社で2ヶ月以上の滞納（未完済） | −70 |
| `own_late_serious` | 同（完済済み） | −55 |
| `own_late_minor` | その社で短期の遅延 | −25 |
| `own_clean` | その社での利用歴あり・滞納なし | **+10** |

> **営業上の鉄則：一度代位弁済を出した保証会社には二度と出さない。**
> 信用情報は5年で消えますが、保証会社の自社DBは消えません。

### ② 他社保証会社での事故

**どの経路で伝わるかで扱いが変わります。**

| ruleId | 条件 | 点数 |
|---|---|---:|
| `licc_subrogation` | LICC加盟社での代位弁済 → LICC参照社 | −100 × licc weight（**ハードリジェクト**） |
| `licc_late` | LICC加盟社での2ヶ月以上の滞納 → LICC参照社 | −50 × licc weight |
| `cgo_history` | CGO加盟社での代位弁済 → CGO加盟社 | −40 × cgo weight（＝実質 −10 程度） |
| `other_history_indirect` | 参照経路のない他社での代位弁済 | −8（申込書の記載から発覚しうる分） |

> **CGOの weight を 0.25 と低く設定している理由**は、
> 「CGOは会員間で滞納情報を共有していない」とされるためです（二次情報）。
> **ここは一次確認が必要な項目です。** 共有していることが判明したら
> `companies.ts` の `cgo.weight` を 0.9 に上げるだけで、全社の判定が正しく変わります。

### ③ 信用情報（本人申告）

**参照しない会社（`weight === 0`）には、これらの減点を一切適用しません。**
代わりに「この会社は信用情報機関を参照しないため影響しにくい」という
**説明用の理由**（`credit_not_referenced`）を付けます。営業がお客様に説明できるようにするためです。

| ruleId | 条件 | 点数（× credit weight） |
|---|---|---:|
| `credit_current_delinquency` | 現在延滞中 | −100（w≧0.8で**ハードリジェクト**） |
| `credit_serious_unresolved` | 61日/3ヶ月以上の延滞・未完済（＝異動） | −100（同上） |
| `credit_serious_resolved` | 同・完済済み | −50 |
| `credit_serious_expired` | 同・6年以上前（保有期限経過） | −5 |
| `debt_recent` | 5年以内の債務整理（任意整理 −90／個人再生・破産 −100） | 同左（w≧0.8で**ハードリジェクト**） |
| `debt_borderline` | 6〜7年前の債務整理 | −30 |
| `debt_expired` | 8年以上前の債務整理 | −5 |
| `mobile_installment` | 携帯端末分割の2ヶ月以上の遅れ | −95 × **CIC weight** |
| `utility_only` | 通信料金のみの遅れ | −3 |
| `borrowing_4plus` | 借入4件以上 | −28 |
| `borrowing_3` | 借入3件 | −10 |
| `no_credit_history` | クレヒス皆無 | −15 |
| `guidance_low` / `guidance_high` | CICクレジット・ガイダンスのスコア帯（任意申告） | −25 / +8 |

**`mobile_installment` だけは JICC ではなく CIC の weight を主に使います。**
携帯端末の分割払いは個別信用購入あっせんとしてCICに登録されるためです
（JICC側は 0.6 倍で参照）。

### ④ 支払能力・属性（全社共通、channel なし）

**信用情報を参照しない独立系では、ここが審査の中心になります。**

| ruleId | 条件 | 点数 |
|---|---|---:|
| `rent_ratio_over40` | 家賃 > 月収の40% | −32 |
| `rent_ratio_over33` | 家賃 > 月収の33% | −16 |
| `rent_ratio_good` | 家賃 ≦ 月収の25% | **+8** |
| `employment_unemployed` | 無職 | −38 |
| `employment_welfare` | 生活保護 | 信販系 −45／その他 **−16** |
| `employment_parttime` | パート・アルバイト | −14 |
| `employment_student` | 学生 | −12 |
| `employment_selfemployed` | 自営業・フリーランス | −10 |
| `employment_pension` | 年金受給 | −10 |
| `employment_dispatch` / `contract` | 派遣／契約社員 | −8 / −6 |
| `tenure_short` | 勤続6ヶ月未満 | −10 |
| `no_emergency_contact` | 緊急連絡先なし | **−55** |
| `emergency_contact_friend` | 緊急連絡先が友人 | −10 |
| `no_own_mobile` | 本人名義の携帯なし | −18 |
| `residence_short` | 在留期限まで12ヶ月未満 | −12 |
| `guarantor_present` | 連帯保証人を立てられる | **+12** |
| `savings_ok` | 家賃6ヶ月分以上の預貯金 | **+8** |
| `credit_clean` | 信用情報上の問題の申告なし | **+6** |

> **緊急連絡先なし（−55）は単独で全社を △ 以下に落とします。**
> 実務上これは書類要件であり、信用情報より優先して確認すべき項目です。
> 本システムでこれを重く置いているのは、**営業が最初に潰すべき論点だから**です。

## 3. 「？」（情報不足）の扱い — ここが実用性を決めます

**判定を出せないときに、それっぽい判定を出さない。** これを厳密に実装しています。

### 3-1. 会社ごとに「必要な情報」が違う

| 会社 | 判定に必要な情報 |
|---|---|
| 日本セーフティー（信用情報を見ない） | 支払能力 ＋ 保証会社利用歴 |
| エポス・オリコ・セゾン・エルズ（見る） | 支払能力 ＋ 保証会社利用歴 ＋ **信用情報** |

そのため、**信用情報を一切ヒアリングできていない段階でも、
日本セーフティーだけは ○ と判定できます。**
これは営業現場で非常に有用です（初回相談の電話口で使える）。

```
入力：年収・雇用形態は聞けた。保証会社利用歴も聞けた。信用情報は未確認。

　日本セーフティー   ○   判定可能
　Casa              ？   信用情報の確認が必要
　エポス             ？   信用情報の確認が必要
```

### 3-2. 一部だけ不明なら「△に丸める」

不明項目が1つでもある会社は、**スコアが高くても ○ 以上を出しません**（上限62点＝△）。
`capped_by_missing_info` という理由が付き、`missingInfo` に
**具体的な質問文**が返ります。

```
　エポス   △   ※未確認の項目があるため○以上は保留
　　　　　　　　【追加ヒアリング】
　　　　　　　　・携帯・スマホ本体代金の分割払いに2ヶ月以上の遅れがあったか
```

**画面はこの `missingInfo` をそのまま「次に聞くこと」として表示します。**
判定システムであると同時に、**ヒアリング項目のチェックリスト**として機能します。

## 4. 出力例

入力：30代・正社員・年収480万・家賃9万・緊急連絡先=親族・
　　　3年前に61日以上の延滞（未完済）・その他問題なし

| 保証会社 | 判定 | 理由 |
|---|:---:|---|
| 日本セーフティー | **○** | 日本セーフティーは個人信用情報機関を参照しないため、クレジットカード等の情報は審査に影響しにくいと考えられます |
| 日本インシュア | **△** | 過去に61日以上の延滞があり完済が確認できていません（JICC加盟は未確認のため影響を限定的に評価）※要確認 |
| Casa | **△** | 同上（規程上はJICC加盟だが実務は自社DB優先とみられるため影響を半減で評価）※要確認 |
| 全保連 | **△** | 同上（JICC加盟が未確認のため）※要確認 |
| エポス | **×** | 過去に61日以上（3ヶ月以上）の延滞があり、完済が確認できていません（CICの「異動」に相当します） |
| オリコ | **×** | 同上 |
| セゾン | **×** | 同上 |
| エルズサポート | **×** | 同上（JICCへの登録・照会を行っているため） |

**推奨アクション**（自動生成）：
> 日本セーフティーを優先してお申込みください。エポス・オリコ・セゾン・エルズサポートへの申込は避けてください。

## 6. weight のチューニング方針（Phase 2以降）

`companies.ts` の `weight` は、**現時点では調査に基づく仮置き**です。
申込実績が溜まったら実測値で置き換えます。

```
新しい weight = 実測の否認率 ÷ そのルールに該当した申込の割合
```

**具体的な運用**

1. 申込のたびに `assessment_id` と実際の結果（承認/否認/条件付）を記録する
2. 四半期ごとに、ルール別・会社別のクロス集計を出す
3. 「Casa に JICC事故ありで出した20件のうち18件が承認された」
   → `casa.jicc.weight` を 0.5 → 0.2 に引き下げる
4. 逆に否認が続いたら引き上げる

**この補正ループを回せるかどうかが、このシステムの寿命を決めます。**
Phase 1 の時点から結果記録を必ず実装してください（→ [04](04-system-spec.md) §3）。

## 7. 調査結果を反映する方法（コード変更不要）

一次確認が取れたら、`src/lib/guarantee/companies.ts` の該当箇所を書き換えるだけです。

```ts
// 例：全保連のJICC加盟が同意書で確認できた場合
jicc: {
  access: 'yes',      // 'possible' → 'yes'
  weight: 1,          // 0.5 → 1
  confidence: 'high', // 'low' → 'high'
  verified: true,     // false → true  ← 画面の「※要確認」が消える
  sources: ['https://www.zenhoren.jp/consent/'],
},
```

- `verified: false` の会社は、判定に `hasUnverifiedBasis: true` が立ち、
  **画面に「※この判定は未確認の前提に基づきます」と表示されます。**
- `tests/guarantee.test.ts` が期待値を固定しているため、
  **weight を変えるとテストが落ちて気づけます。** 意図した変更ならテストも更新してください。
