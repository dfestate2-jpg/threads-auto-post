# 02. 既存サービス・システム・API 調査

依頼事項③への回答。

---

## 1. 結論

**「お客様の信用情報から、保証会社ごとの審査通過可能性を判定する」既存サービス・API は存在しません。**

理由は明快で、**そもそも作れないから**です（→ §3）。
したがって独自開発が必要ですが、**当初構想のままでは開発してはいけません**（→ [03](03-legal-compliance.md)）。

---

## 2. 調査対象と結果

### 2-1. 信用情報機関が提供するAPI

| 機関 | 第三者向けAPI | 状況 |
|---|---|---|
| CIC | **なし** | 照会は**加盟会員のみ**。加盟資格は割賦販売法・貸金業法上の事業者に限られ、不動産仲介業者は加盟できない |
| JICC | **なし** | 同上。加盟には貸金業・保証業等の事業実態と審査が必要 <https://www.jicc.co.jp/aboutus/member-entry> |
| 全国銀行個人信用情報センター | **なし** | 銀行・銀行系保証会社のみ |

**本人開示は API 化されていません。**
- CIC：インターネット開示。結果は**PDFで画面表示**（機械可読なCSV/JSON提供なし）
- JICC：スマホアプリ／郵送。結果はPDFまたは書面

→ **自動連携は技術的にも制度的にも不可能です。**

### 2-2. 「クレジット・ガイダンス」（CIC）— 唯一の準スコアAPI的存在

- 2024年11月28日：**本人向け**提供開始
- 2025年4月1日：**加盟会社向け**提供開始
- 内容：**スコア**＋**算出理由 最大4つ**。年齢・性別・勤務先・居住地域は算出から除外
- <https://www.cic.co.jp/credit-guidance/>

> **これは重要です。** 本人が自分のスコアを1,500円（郵送）／インターネット開示で確認でき、
> **数値1つ＋理由4つ**という極めて構造化された形で得られます。
> 生の開示報告書全体より情報量が圧倒的に少なく、
> **「保証会社に見せるための書類」ではなく「本人が自分の状態を知るための指標」**です。
>
> ただし**これも第三者への提出は推奨されていません**（→ [03](03-legal-compliance.md)）。
> 本システムでは「お客様がご自身で確認したスコア帯を、選択肢から選んでいただく」形で
> 参考入力として受け取る設計にしています（数値の直接保管はしない）。

### 2-3. 賃貸業界の既存サービス

| カテゴリ | 例 | 保証会社別の通過判定機能 |
|---|---|:---:|
| 賃貸管理SaaS | いい生活、いえらぶCLOUD、ESいい生活賃貸管理クラウド | **なし** |
| 電子申込・入居申込 | イタンジ（申込受付）、いえらぶ 等 | **なし**（申込を保証会社へ中継するだけ） |
| 保証会社の自社審査システム | 全保連・Casa等の即時審査 | **その社の審査結果のみ**。他社との比較不可 |
| 審査特化の仲介会社 | エース不動産 等 | **人手のノウハウ**。システム化されていない |
| 簡易診断コンテンツ | 「60秒で終わる賃貸入居審査診断」等 | **集客用の簡易チェックリスト**。信用情報は扱わない |

→ **既存の賃貸SaaSはどれも「申込を送る」までで、「どこに送るべきか」は判定しません。**
　ここが空白地帯であり、貴社が作る価値がある領域です。

### 2-4. 与信スコアリングの汎用サービス

金融向けのスコアリングエンジン（オルタナティブデータ活用等）は複数存在しますが、
- 入力に **CIC/JICC の生データを前提**とするものは、加盟会員向けであり利用不可
- 家賃債務保証の審査基準（LICC/CGO/自社DB）をモデル化したものは**存在しない**

### 2-5. 開示報告書のOCR解析ツール

債務整理を扱う法律事務所向けに CIC 開示報告書を読み取るツールが存在するか調査しましたが、
**公開された製品として特定できませんでした。**
（法律事務所は「受任した債務者本人の代理人」という立場であり、本件とは法的な位置づけが根本的に異なります。
　仲介会社が同じことをしてよい根拠にはなりません。）

## 3. なぜ既存サービスが存在しないのか（＝作るときの制約）

| 理由 | 内容 |
|---|---|
| **① 信用情報にアクセスできない** | 加盟会員以外は照会不可。本人開示の第三者提出は各機関が明確に否定（→ [03](03-legal-compliance.md)） |
| **② 保証会社が審査基準を公開しない** | 審査基準は各社の営業秘密。公式に「こうすれば通る」は絶対に出ない |
| **③ 正解データが手に入らない** | 「申込 → 承認/否認」のペアデータを持っているのは保証会社自身か、大量に申込を出す仲介会社だけ |
| **④ 基準が動く** | 全保連のJICC加盟（とされる2022年）のように、系統自体が変わる。静的なルールは陳腐化する |

> **③が本質です。**
> このシステムの精度は、外部データではなく
> **「貴社が過去に出した申込と、その結果」の蓄積量で決まります。**

---

## 4. だから作るべきものは「判定器」ではなく「学習する台帳」

```
　　　既存サービスがないから作る、ではなく
　　　貴社しか持っていないデータがあるから作る
```

貴社が持っている（あるいはこれから持てる）唯一無二のデータ：

| データ | 現状 | システム化後 |
|---|---|---|
| 誰を、どの保証会社に出したか | 担当者の記憶・紙 | **DBに構造化** |
| その結果（承認/否認/条件付き） | 担当者の記憶 | **DBに構造化** |
| 否認理由（保証会社から聞けた範囲） | 断片的 | **DBに構造化** |
| お客様の属性・自己申告の信用状態 | 申込書のみ | **DBに構造化** |

これが200〜300件たまると、
**「当社の顧客層において、この属性なら日本セーフティーは実測◯%通っている」**
という、どのベンダーも持っていない数字が出ます。

**推奨する開発順序**

1. **Phase 1**：ルールベース判定（本ドキュメントの調査結果をそのままコード化）＋ 申込結果の記録
2. **Phase 2**：実績が溜まったら、ルールの重みを実測値で補正
3. **Phase 3**：件数が十分になったらロジスティック回帰等で統計モデル化（説明可能性は維持）

**Phase 1 の時点で営業判断には十分役立ちます。**
そして Phase 1 から結果記録を必ず入れることが、Phase 2/3 の前提条件です。
**ここを後回しにすると1年分のデータを失います。**
