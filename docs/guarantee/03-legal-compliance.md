# 03. 法律・個人情報保護・信用情報機関の規約上、問題のない方法

依頼事項④の前提となる、**最重要ドキュメント**です。

> 免責：本書は一次情報に基づく整理であり、法律意見ではありません。
> 実装前に必ず**貴社顧問弁護士のレビュー**を受けてください。
> 特に §2 の論点は、事業の可否そのものに関わります。

---

## 1. 結論：当初フローは実装してはいけない

```
❌ お客様情報入力
❌   ↓
❌ CIC・JICC等の信用情報を本人が取得・アップロード      ← ここが規約違反
❌   ↓
❌ AIが信用情報を解析（サーバに保存して解析）           ← ここも規約違反
❌   ↓
　　過去の家賃滞納・保証会社利用履歴も入力
　　↓
　　保証会社ごとに審査通過可能性を表示
```

## 2. 何に抵触するのか

### 2-1. CIC の立場

**FAQ「開示した結果を、不動産会社や自分が勤務する会社に提出して見せてもいいのですか？」**
に対し、CIC は
**「開示した内容を不動産会社や勤務先に提出したり見せたりしないでください」**という趣旨で回答しています。
理由として「開示された信用情報はプライバシーの観点から重要な情報であり、
第三者に提出・提示することでご自身の権利が害されるおそれがある」と説明。

- <https://www.cic.co.jp/faq/detail/report/002570.html>
- **2026年1月27日付お知らせ「『信用情報開示報告書』のお客様ご自身による第三者への提供」**
  <https://www.cic.co.jp/news/info/2026/01/daa5655238a882776cd8214ae7e862820cd47a21.html>
  - 開示報告書には契約内容・借入額・残債・支払状況等の機微な情報が含まれるため、
    第三者への安易な提供を避けるよう注意喚起

> **注目すべきは、CICがこれを 2026年1月に改めて掲出していることです。**
> 「本人に開示させて提出させる」事業者が現に増えており、CICが問題視しているということです。
> **これから作るシステムが、まさにその対象になります。**

### 2-2. JICC の立場（より厳格）

**注意事項「第三者等からの信用情報記録開示書の提出要求について」**
- <https://www.jicc.co.jp/notes/a045i000008Mfq3AAC>
- 「第三者から開示書の提出を求められ、応じたことでトラブルになった事例がある」
- 開示制度は**本人が自分の登録内容を確認するための制度**であると明示

**FAQ「開示結果を不動産会社や勤務先等の第三者に提出してよいですか？」**
- <https://www.jicc.co.jp/faq/detail/a095i000000LtgdAAC>
- 開示結果を第三者へ提供したことで生じた損害について**JICCは一切責任を負わない**

**さらに開示サービスの利用規約上、**
**「第三者が開示結果を収集・蓄積・利用する目的で、本人に開示を受けさせる行為」が禁止されています。**

> **これが決定的です。**
> 当初構想は、まさに
> 「当社（第三者）が、蓄積・利用する目的で、お客様に開示を受けさせ、提出させる」
> 行為に該当します。**JICCの規約に明文で反します。**

### 2-3. 個人情報保護法上の論点

規約以前に、法律上も負荷の高い設計です。

| 論点 | 内容 |
|---|---|
| 利用目的の特定・通知 | 「保証会社の選定のため」と特定して明示する必要（法17・21条） |
| **取得の適正性** | 信用情報機関が明確に反対している手段での取得が「適正な取得」（法20条）といえるか、疑義がある |
| 安全管理措置 | 借入残高・延滞情報は極めて機微。漏えい時のレピュテーション損害が甚大（法23条） |
| 第三者提供 | 判定結果をオーナー・管理会社に共有する場合は別途同意が必要（法27条） |
| 保有期間 | 目的達成後の速やかな消去（法22条） |
| **要配慮個人情報ではない** | 信用情報・債務整理歴は法2条3項の要配慮個人情報には**該当しない**。ただし機微情報として厳格運用すべき |

### 2-4. その他

| 論点 | 内容 |
|---|---|
| 宅建業法 | 直接の禁止規定はないが、「信用情報の提出を条件に媒介する」運用は重要事項説明・誠実義務の観点で問題になりうる |
| 差別的取扱い | 判定結果を理由に**入居の申込自体を拒む**運用は、住宅セーフティネット法の趣旨および人権上の問題になりうる。**「どの保証会社を優先するか」の内部判断に留めること** |
| 保証会社との協定 | 保証会社との代理店協定に「申込前に信用情報を取得しない」旨の条項がないか要確認 |

## 3. では、どう作るか — 適法な代替設計

### 設計原則（この4つを守れば成立します）

```
原則1： 開示報告書そのものを、当社が受領・保管・送信しない
原則2： 当社が受け取るのは、お客様が自ら選択・申告した「事実」だけ
原則3： お客様は、開示を受けること自体を強制されない（任意であることを明示）
原則4： 判定は「保証会社の選定」にのみ使い、入居可否の判断には使わない
```

### 適法な3層構造

```
┌─────────────────────────────────────────────────────┐
│ 層1【必須・完全に適法】 本人ヒアリング（選択式）              │
│   「過去5年以内に、クレジットカードの支払いを              │
│     61日以上または3ヶ月以上遅れたことがありますか？」        │
│      → はい / いいえ / わからない                          │
│   ※ 開示書を見なくても、本人が知っている事実                  │
│   ※ これだけで判定精度の 7〜8割は出ます（→ §4）             │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ 層2【必須・完全に適法】 自社申込履歴DB                       │
│   貴社が過去に出した申込と結果。最も価値が高い                │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ 層3【任意・要注意】 お客様ご自身による自己確認の結果          │
│   お客様が自分の端末で開示を確認し、                         │
│   「異動情報の有無」等を "選択肢から選んで" 入力              │
│   ※ 当社は開示書ファイルを受け取らない・保存しない            │
│   ※ 「開示してください」と当社から求めない（案内に留める）    │
└─────────────────────────────────────────────────────┘
```

### やってよいこと / やってはいけないこと

| ✅ やってよい | ❌ やってはいけない |
|---|---|
| 「延滞したことがありますか」と選択式で聞く | 開示報告書のPDF/画像をアップロードさせる |
| お客様が自分で開示する方法を**情報提供**する | 当社が開示を**要求・条件化**する |
| お客様が確認した結果を**本人の申告として**受け取る | 開示書ファイルをサーバに保存する |
| 「異動あり/なし/わからない」のフラグを保存する | 借入先名・残高・契約番号を保存する |
| 判定結果を営業の内部資料として使う | 判定結果をオーナー・管理会社に無同意で渡す |
| 自社の申込結果を蓄積する | 他社顧客の情報を流用する |
| 開示代行を**しない** | 開示代行サービスを提供する（規約違反かつ有償なら他法令リスク） |

### 【任意・Phase 4】どうしても開示書を読み取りたい場合

**サーバに送らない構成なら、リスクを大幅に下げられます。**

```
お客様のブラウザ内（クライアントサイド）でのみ PDF を読み取り
  → その場で「異動:有無」「延滞:有無」等のフラグに変換
  → 変換後のフラグだけを送信
  → PDF本体は一度もネットワークに出ない・保存されない
```

- 実装：`pdf.js` + WASM OCR をブラウザで実行。ファイルは `File` オブジェクトのまま保持し送信しない
- 画面に「このファイルは当社サーバに送信されません」と明示し、技術的にもそれを担保する
- **それでも「第三者が利用する目的で本人に開示を受けさせる」構成に近づくため、
  弁護士確認を必須とし、当社から開示を求める文言は一切使わないこと**

> **推奨は Phase 1〜2 で運用を開始し、Phase 4 は必要性が実証されてから検討することです。**
> §4 の通り、層1だけで実用精度に達します。

## 4. 「開示書を見なくても精度は落ちない」根拠

判定に本当に効くのは、以下の**8個のフラグ**だけです。

| # | フラグ | 開示書が必要か | 本人が知っているか |
|---|---|:---:|:---:|
| 1 | その保証会社での滞納歴 | 不要 | **知っている** |
| 2 | 他社保証会社での代位弁済歴 | 不要 | **知っている** |
| 3 | 61日/3ヶ月以上の延滞（＝異動）の有無 | あると確実 | **概ね知っている** |
| 4 | 債務整理・自己破産の有無と時期 | 不要 | **確実に知っている** |
| 5 | 携帯端末分割の滞納 | あると確実 | 忘れがち ← ここだけ弱い |
| 6 | 現在の延滞の有無 | 不要 | **知っている** |
| 7 | 借入件数のレンジ | 不要 | **知っている** |
| 8 | 完済済みか | 不要 | **知っている** |

**開示書が本当に効くのは #5（携帯端末の分割滞納）だけ**です。
これは本人が「携帯代を数回遅れた」程度にしか認識しておらず、
実際にはCICに登録されているケースが多いためです。

**対策：開示書を取らずに #5 を拾う。**
以下の質問を入れれば、実務上ほぼカバーできます。

> 「携帯電話・スマートフォンの**本体代金を分割払い**にしていて、
> 　その支払いを**2ヶ月以上**遅れたことはありますか？
> 　（通信料金だけの遅れは含みません）」
> 　→ はい / いいえ / わからない

「わからない」が選ばれた場合は、システムが自動的に
**信販系3社の判定を `△` に丸め、「※要確認」を表示**します。
これは「精度が落ちる」のではなく、**不確実性を正しく表示している**ということです。

## 5. 同意取得の実装要件

お客様から取得すべき同意は**1つだけ**です（開示書を受け取らないため、非常にシンプルになります）。

**同意文（案）**

> ■ 保証会社選定のための情報のお取り扱いについて
>
> 当社は、お客様に最も適した賃貸保証会社をご提案するため、
> お客様にご申告いただいた以下の情報を利用します。
>
> ・お客様の属性情報（年齢、雇用形態、収入、ご希望物件の家賃 等）
> ・過去の賃貸保証会社のご利用状況・お支払い状況に関するご申告
> ・お支払い遅延、債務整理等の有無に関するご申告
>
> 【重要】
> ・当社は、信用情報機関（CIC・JICC等）の**開示報告書そのものをお預かりしません**。
> 　開示報告書のご提出は**不要**です。ご提出をお願いすることもありません。
> ・ご申告は**任意**です。ご申告いただかない項目は「不明」として扱い、
> 　その旨を判定結果に表示します。ご申告がないことを理由に
> 　お部屋のご紹介をお断りすることはありません。
> ・判定結果は、**保証会社のお申込み先を決めるためだけ**に利用します。
> 　実際の審査は各保証会社が行うものであり、本判定は結果を保証するものではありません。
> ・情報の保存期間は、ご契約またはご相談終了後 ◯ヶ月とし、以後速やかに削除します。
> ・お客様は、いつでも当該情報の開示・訂正・利用停止・削除をご請求いただけます。
>
> □ 上記に同意します

**実装上の要件**

| 要件 | 実装 |
|---|---|
| 同意の記録 | 同意日時・同意文バージョン・IPをDBに保存 |
| 同意の撤回 | 撤回API＋論理削除→物理削除ジョブ |
| **アップロード機能を作らない** | ファイル入力UIをそもそも実装しない（誘惑を断つ） |
| 保存項目の最小化 | 借入先名・残高・契約番号・カード番号は**スキーマに存在させない** |
| 暗号化 | 機微フラグはアプリケーション層で暗号化して保存 |
| アクセス制御 | 担当営業と管理者のみ。閲覧ログを全件記録 |
| 保存期間 | 既定6ヶ月。バッチで自動削除 |
| 判定理由の記録 | 「なぜその判定になったか」を保存（説明責任・法27条対応） |

## 6. 運用ルール（システムだけでは守れない部分）

| ルール | 理由 |
|---|---|
| **お客様に「CICを開示してきてください」と言わない** | 当社が要求すれば規約違反構成に近づく |
| **開示報告書を見せられても受け取らない・複製しない** | 受領した時点でリスクが発生する。「拝見はしません」と伝える |
| 判定 `×` を理由に物件紹介を断らない | 差別的取扱いの疑義。あくまで保証会社の選定にのみ使う |
| 判定結果をお客様に見せる場合は表現に注意 | 「審査に落ちます」ではなく「他社を優先してご提案します」 |
| 判定結果をSNS・チャットに貼らない | 機微情報の漏えい |
| 年1回、各社の同意条項を棚卸しする | 全保連の例のように系統が変わる |
