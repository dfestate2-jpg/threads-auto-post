# 10. 銀行入金 → Googleスプレッドシート 自動反映

> 会社の銀行口座（ドコモの銀行＝ドコモSMTBネット銀行）への入金を自動で取得し、
> 既存の入金管理スプレッドシートへ **入金日 / 入金者 / 入金額** を重複なく積み上げる。

---

## 0. 調査結果 — どの経路で明細を取るか

### 0-1. 「ドコモ銀行」の特定

住信SBIネット銀行は **2026年8月3日に「ドコモSMTBネット銀行」へ商号変更**された（ドコモの銀行）。
金融機関コード・支店番号・支店名・口座番号に変更はなく、旧行名での振込受付は2026年10月30日まで。
2025年10月1日にNTTドコモの連結子会社となり、ドコモと三井住友信託銀行の共同経営体制になったことに伴う変更。

本ドキュメントは、この **ドコモSMTBネット銀行の法人口座** を前提としている。
（もし対象が「ドコモ口座」等の別サービスであれば取得経路が変わるため、着手前に口座の銀行名を確認すること。）

### 0-2. 取得方式の比較

| # | 方式 | 実現性 | 追加費用 | 規約 | 判定 |
|---|------|--------|----------|------|------|
| ① | 銀行の参照系API（残高・入出金明細照会）を自社が直接叩く | **×** | — | — | 銀行のAPI接続サービスは、**電子決済等代行業者として登録した提携先企業向け**の枠組み。一般の事業会社が単独でAPIキーの発行を受ける窓口は公開されていない |
| ② | **freee会計の口座同期（API連携方式）＋ freee Public API** | **◎** | **¥0** | 公式API | **採用** |
| ③ | マネーフォワード クラウド ＋ MF API | ○ | 別契約が必要 | 公式API | freee を既に使っており二重契約になる |
| ④ | 全銀フォーマットの入出金明細伝送 / 明細CSVの手動ダウンロード | △ | 銀行の伝送サービス料 | 公式 | 「自動で取得する」部分を別途作り込む必要がある。人手が残る |
| ⑤ | ネットバンキングのスクレイピング | **×** | — | **規約違反の恐れ** | 依頼どおり採用しない |

### 0-3. ② を採用した理由

- **銀行のログイン情報を本システムが一切持たない。**
  freee の「API連携方式」は、freee と銀行がAPIで直接つながる方式で、freee 側もネットバンキングの
  ID・パスワードを保持しない。本システムはさらにその外側で、freee のAPIを読むだけ。
- **追加費用が発生しない。** freee は既に契約済みで、freee Public API の利用料は無料。
- **会計と数字が二重管理にならない。** 経理が見ている明細と同じものをシートに載せる。
- **取得方式を後から変えても本システムは動く。**
  仮に対象口座がAPI連携方式に対応していなくても、freee側を
  「スクレイピング方式」「明細CSVのアップロード」に切り替えれば、
  本システムから見える口座明細（wallet_txns）は同じ形で読める。**アプリ側の改修は不要。**

### 0-4. 着手前に確認すること（1つだけ）

**freee会計で、対象のドコモSMTBネット銀行 法人口座を「API連携方式」で同期できるか。**
freee ヘルプセンターの「freee会計と連携（同期）できる口座」一覧、または freee の
［口座を登録・同期］画面で銀行名を検索して確認する。
API連携方式の対象であれば、freee 側の同期設定を済ませるだけで準備は完了する。

### 0-5. この経路の制約（把握しておくこと）

| 制約 | 内容 | 影響 |
|------|------|------|
| リアルタイムではない | freee の銀行同期は1日数回。着金からfreeeへの反映まで数時間〜1日程度かかる | 「着金の瞬間にシートへ載る」ことは保証しない。**当日中〜翌営業日に載る** |
| 入金者名は銀行が送る摘要そのまま | `ﾌﾘｺﾐ ｶ)ﾀﾏﾎｰﾑ` のような半角カナ。契約者名とは限らない | 本システムで整形する（後述）。契約者名（B列）は従来どおり人が入れる |
| freee のプランによる制限 | 口座同期・Public API の利用可否はプランに依存する場合がある | 現行プランで口座同期が使えていれば問題ない。ミニマムプラン等で制限に当たる場合は要確認 |

## 4. システム構成

```
  ┌─────────────────────────┐
  │ ドコモSMTBネット銀行      │  会社の法人口座に入金が発生
  │ （旧 住信SBIネット銀行）   │
  └────────────┬────────────┘
               │ 銀行 ⇄ freee のAPI連携方式（1日数回の自動同期）
               │ ※ 本システムは銀行のIDもパスワードも持たない
               ▼
  ┌─────────────────────────┐
  │ freee 会計              │  「自動で経理」の口座明細として蓄積
  └────────────┬────────────┘
               │ freee Public API
               │ GET /api/1/wallet_txns?entry_side=income
               ▼
  ┌───────────────────────────────────────────────────┐
  │ 本システム（Next.js / Netlify）                       │
  │                                                   │
  │  30分ごと ─▶ /api/cron/bank-deposits              │
  │                  │                                │
  │                  ├─① 入金だけ取得（過去14日分）      │
  │                  ├─② 摘要 → 入金者名に整形          │
  │                  ├─③ DBへ確保（UNIQUE制約）★重複防止 │
  │                  ├─④ シート末尾と突合   ★重複防止    │
  │                  └─⑤ 未反映分だけ追記 → SYNCED確定   │
  └────────────┬──────────────────────────────────────┘
               │ Google Sheets API v4（サービスアカウント）
               │ values.append（末尾に行を挿入）
               ▼
  ┌─────────────────────────────────────────────┐
  │ 既存スプレッドシート                            │
  │   シート名 = 入金月（202608 …）                 │
  │   2行目: 見出し / 3行目〜: データ                │
  │   A:入金日  B:契約者名  C:入金者  D:入金額       │
  │   E:契約締結日  F:備考                          │
  │   ↑ システムが書くのは A・C・D だけ。B/E/F は人   │
  └─────────────────────────────────────────────┘
```

### 4-1. 既存シートの構造に合わせている点

いただいたスプレッドシートの実際の運用に、次のとおり合わせている。

| 既存の運用 | 本システムの動作 |
|-----------|-----------------|
| 月ごとにシートを分け、名前は `yyyyMM`（例 `202608`） | 入金日の月のシートへ書く。無ければ **「コピー」シートを複製**して自動作成 |
| 見出しは2行目、データは3行目から | 3行目以降の末尾に追記 |
| A:入金日 / B:契約者名 / C:入金者 / D:入金額 / E:契約締結日 / F:備考 | **A・C・D のみ**書き込む。B・E・F は空のままにして人が埋める |
| 同じ入金日が続くとき、2行目以降のA列は空欄 | 同じ挙動（`DEPOSIT_OMIT_REPEATED_DATE=0` で毎行に日付を入れることも可） |
| 入金者はカタカナの振込人名義（`タマホーム`, `クラハシ　ジユンヤ`） | 半角カナを全角に直し、`ﾌﾘｺﾐ` などの取引種別と法人格略号 `ｶ)` を落とす |

## 5. 実装手順

### 手順1. freee 側の口座同期（経理担当）

1. freee会計 ＞［口座］＞［口座を登録・同期］
2. **ドコモSMTBネット銀行（法人）** を選び、案内に従って同期を設定する
   - 可能なら **API連携方式** を選ぶ（freee が銀行のID・パスワードを保持しない）
3. 数分待ち、［自動で経理］に **入金明細が並ぶ**ことを確認する
4. 銀行側の利用者権限は **照会のみ**にしておく

### 手順2. freee アプリの作成（導入担当）

1. freeeアプリストア ＞［開発者向け］＞［アプリ管理］＞ 新規アプリ作成
2. コールバックURLに `urn:ietf:wg:oauth:2.0:oob` を登録
3. 発行された `client_id` / `client_secret` を控える

### 手順3. Google 側の準備（導入担当）

1. Google Cloud Console でプロジェクトを作成（既存でも可）
2. **Google Sheets API** を有効化
3. ［IAM と管理］＞［サービス アカウント］でサービスアカウントを作成
4. ［キー］＞［鍵を追加］＞ **JSON** をダウンロード
5. **対象のスプレッドシートを開き、サービスアカウントのメールアドレス
   （`〜@〜.iam.gserviceaccount.com`）を「編集者」で共有する**
   - これを忘れると `403` で失敗する。最も多いつまずきどころ

### 手順4. 環境変数の設定

`.env.example` の「銀行入金 → Googleスプレッドシート 自動反映」の節を参照。

これが手入力済みの行と重複させないための設定。

## 6. セキュリティ上の注意点

| # | 論点 | 本システムの対応 |
|---|------|-----------------|
| 1 | **銀行の認証情報** | **一切保持しない。** 銀行に接続するのは freee であり、本システムは freee のAPIを読むだけ。`.env` に銀行のID・パスワードを書く場所は存在しない |
| 2 | **スクレイピングをしない** | 銀行サイトへのHTTPアクセスは1行も無い。取得は freee の公開APIのみ |
| 3 | **銀行側の権限** | 連携に使う銀行の利用者は **照会のみ**。振込・払戻の権限を与えない |
| 4 | **freee のトークン** | アクセストークンは24時間で失効。リフレッシュトークンは**1回使うと置き換わる**ため、環境変数ではなくDB（`integration_credentials`）で保持し、更新は PostgreSQL のアドバイザリロックで直列化する。並行更新でトークンが壊れることを構造的に防いでいる |
| 5 | **Google の鍵** | サービスアカウントの秘密鍵は環境変数のみ。リポジトリには置かない（`.gitignore` 済み）。権限は「共有した1つのスプレッドシート」に限定され、Googleドライブ全体へは及ばない |
| 6 | **Cronエンドポイントの保護** | `/api/cron/bank-deposits` は `x-cron-secret`（`CRON_SECRET`）のタイミング安全な比較で保護。秘密が一致しなければ401 |
| 7 | **ログに秘密を出さない** | トークン・鍵はログに出さない。トークンの同一性判定にはSHA-256の指紋のみを保存し、生値は保存しない |
| 8 | **書き込み範囲の限定** | 書くのは A・C・D 列だけ。人が入力する B・E・F 列と、他のシートには触らない |
| 9 | **暴走時の被害限定** | 1回の実行で追記できる行数に上限（`DEPOSIT_MAX_ROWS_PER_RUN`、既定200行）。`DEPOSIT_SYNC_ENABLED=0` で即時停止できる |
| 10 | **個人情報** | 振込人名義は個人情報にあたる。DB・スプレッドシートの閲覧権限は必要な担当者に限定すること |

## 7. 重複登録を防ぐ仕組み（依頼の要件③）

「同じ入金が2回シートに載る」ことを、**独立した3つの防御**で防いでいる。
1つが破れても、残りが止める構造にしてある。

### ① `externalId` の UNIQUE 制約 — 取得を何度繰り返しても行は1つ

`bank_deposits.externalId` は `freee:{事業所ID}:{明細ID}` で、DBにUNIQUE制約がある。
毎回14日分をさかのぼって取得するので同じ明細は何度も取れるが、
`createMany({ skipDuplicates: true })` により **2件目以降は物理的に作られない**。

### ② PENDING → SYNCED の二相コミット — 書けた分だけ確定させる

取り込み時は `PENDING`。シートへ追記できたものだけを `SYNCED` に変える。
追記に失敗したものは `FAILED` として残り、**次回の実行で自動的に再試行**される。
（＝通知漏れならぬ「記録漏れ」が起きない）

### ③ シート末尾との突合 — 追記した直後に落ちた分を拾い直す

②の隙間は「追記APIは成功したが、SYNCEDを書く前にプロセスが落ちた」瞬間だけ。
これを埋めるため、追記の前に必ずシートを読み、
**「シート末尾の j 行が、未反映の先頭 j 件と一致するか」** を j が最大になる位置で判定する。

追記は必ず末尾に、未反映の並び順どおりに入るので、この判定で
「すでに書かれている分」を正確に特定できる。
一致した分は追記せず、行番号だけ回収して `SYNCED` にする。

> 副次効果：システムが止まっている間に **人が同じ入金を手入力していた場合も、二重に書かない。**

さらに、ジョブ自体の多重起動は `job_locks` のリース（`WHERE lease_until < now()` を満たした
実行だけが確保できる）で防いでいる。Cron が同時に2つ起動しても、走るのは1つだけ。

### 重複を防ぐ代わりに受け入れているトレードオフ

同じ日・同じ振込人名義・同じ金額の入金が「手入力済みで1件、未反映で1件」ある場合、
③がそれを既出とみなして追記しないことがある。
**依頼の要件が「重複させないこと」を最優先しているため、疑わしいときは追記しない側に倒している。**
月末に件数を突き合わせる運用を推奨する（`bank_deposits` テーブルが正の記録として残る）。

## 8. 運用とトラブルシューティング

### 動いているかの確認

```sql
-- 直近の実行結果
SELECT * FROM cron_runs WHERE job = 'bank-deposit-sync' ORDER BY "startedAt" DESC LIMIT 10;

-- 未反映のまま残っている入金（0件が正常）
SELECT "depositDate", "payerName", amount, status, attempts, error
FROM bank_deposits WHERE status IN ('PENDING','FAILED') ORDER BY "depositDate";
```

`/api/cron/bank-deposits` の応答は次の形。

```json
{ "ok": true, "fetched": 12, "inserted": 3, "skipped": 0,
  "reconciled": 0, "appended": 3, "failed": 0, "durationMs": 1840 }
```

### よくある失敗と対処

| 症状 | 原因 | 対処 |
|------|------|------|
| `Sheets API ... responded 403` | サービスアカウントにシートを共有していない | シートを `〜@〜.iam.gserviceaccount.com` に「編集者」で共有 |
| `freee の再認可が必要です` | リフレッシュトークンが失効（長期間未使用／二重更新） | `npm run freee:auth` をやり直し、`FREEE_REFRESH_TOKEN` を新しい値に差し替える。DBの値も自動で入れ替わる |
| 入金がシートに出てこない | freee 側にまだ明細が来ていない | freee の［自動で経理］を確認。銀行同期は1日数回 |
| 過去の入金が大量に追記されそう | `DEPOSIT_SYNC_START_DATE` が古い | 手入力済みの最終日の翌日に設定し直す。事前に `npm run deposit:dry-run` で確認する |
| 入金者名が読みにくい | 摘要の形が想定外 | `bank_deposits.rawDescription` に生の摘要が残っている。`src/lib/domain/payerName.ts` の除去リストに追記し、`tests/payerName.test.ts` に例を足す |
| 緊急で止めたい | — | `DEPOSIT_SYNC_ENABLED=0` にして再デプロイ |

### 月が替わったとき

新しい月のシートは、最初の入金が発生した時点で **「コピー」シートの複製として自動作成**される。
人の作業は不要。テンプレートの名前を変える場合は `DEPOSIT_TEMPLATE_SHEET_TITLE` を合わせる。
